Executive decision
Keep the shared editor, native PHP plugin, modular TypeScript API, PostgreSQL authority, Redis/BullMQ transport, dedicated workers and independent static serving. Do not add infrastructure just to make the architecture larger. Make the hot paths do less work, make every accepted mutation recoverable, and make every release claim depend on real evidence.
This Version 4 supersedes Version 3 as the controlling proposed plan. It preserves the earlier security, portability, commercial, privacy and operational scope while specifying editor subscriptions and save races, incremental dependency builds, physical data constraints, exact request shapes, publication-state guards, finite resource limits, cache identities, worker scheduling, WordPress hot paths and interleaved failure tests. Account and membership authority now precede tenant-facing operation storage and features. Existing features are inventoried before extraction so speed work cannot silently remove capability.
The companion engineering pack contains reference contracts, synthetic fixtures, an endpoint catalogue, candidate performance budgets, a feature-discovery ledger, an updated dependency backlog and a check script. Its local schema/example/dependency checks are distinct from application verification; application and hosting tests remain not run. Reference schemas deliberately cover a small first-party widget vocabulary and must be extended through reviewed runtime contracts, not used to discard unknown existing widgets.
The implementation objective: the user can identify what is saved, what is authoritative, what is active, what is verified, what is blocked, and what recovery is safe. Speed must not come from dropping durability, skipping authorization, weakening validation or pretending a queued job is a published website.

1. Scope and production-readiness verdict
1.1 What is already sound in Version 3
The previous plan correctly separates drafts from releases, cloud storage from WordPress storage, queued commands from Kafka events, and local editing from optional cloud services. It also calls for durable acceptance, receipts, safe retries, native PHP rendering, migration preservation, and independent public serving. Those decisions remain. [B1]
The most important improvement is moving from principles to implementation contracts. “Tenant isolation” becomes a context-propagation and negative-test matrix. “Atomic publishing” becomes a stated boundary, a conditional activation operation, and handling of partial native WordPress side effects. “Backups” becomes a restore sequence that fences writers and reconciles external effects. “Production-grade” becomes a gate with evidence, owners, and unresolved-risk rules.
1.2 What this document does not establish
It does not establish that current main still contains each historical defect, that the application builds, that the plugin runs on a particular host, that all referenced dependency versions interoperate, or that any SLO has been achieved. It is not a claim of regulatory certification, penetration-test completion, unlimited scale, or universal WordPress/theme compatibility.
The deployment provider, region, commercial support promise, final retention schedule, supported-version matrix, pricing model, and staffing must be approved before a production release. Appendix C makes these choices visible instead of hiding them in assumptions. Work that does not depend on those choices can proceed.

2. Product journeys and release scope
2.1 Three hosting journeys

Connected mode is not unconditional two-way synchronization. A cloud-authoritative page does not silently become editable in WordPress because the connection fails. Offer a fork or explicit authority recovery; keep independently local pages editable.
2.2 Minimum releasable product
The first releasable core should support accounts/workspaces for cloud use, site/page management, the shared editor, responsive layout, a documented core-widget set, draft save/load, undo/redo, media, revisions, preview, publish, rollback/restore, portability reports, and understandable operation status. Native WordPress must support these core local capabilities without cloud login. Connected release adds verified setup, asset transfer, ownership, conflict handling, and destination receipts.
Initial core widgets: container/layout, heading, rich text, image, button/link, divider, spacer, list, and a supported navigation model. Forms are a separately gated dynamic slice. Galleries, popups, advanced motion, commerce, external feeds, and third-party widgets are enabled only after their runtime, security, and parity contracts pass. Preserve existing content for widgets not yet certified; do not remove it during migration.
2.3 Explicitly separate feature projects
Existing Elementor import, third-party Elementor widget execution, unrestricted custom-code marketplaces, real-time multi-author merging, full commerce, arbitrary PHP execution, and universal plugin/theme support are not implicit promises. Define compatibility projects for them. SFTP stays unavailable until a real transfer and verification adapter is certified. Optional AI produces reviewable changes through normal document commands.
Core local WordPress operation must not be disabled by an expired cloud subscription, a telemetry endpoint, remote font loading, or a license-service outage. Cloud storage and hosted extras can have their own transparent entitlements and retention policies. [B1]
2.4 Feature accounting: preserve the product, not only the new core
Before extraction, create one capability record for every discovered route, visible editor control, widget type, import/export format, background task, and third-party integration. The initial catalogue in the engineering pack is a discovery checklist, not a claim that the repository implements all entries. Record actual source paths only after inspection. Each record contains capability ID, user journey, persisted fields, current behavior, known limitations, host support, representative fixture, replacement owner, and migration disposition.
A smaller certified first release is permitted only as an explicit product decision. It is not permission to silently remove an existing customer's gallery, popup, custom CSS, dynamic binding, or payment control. A feature is either preserved and verified, retained safely on a supported legacy path with a retirement date, or disabled with a documented compatibility report and a preserved export. Never render a broken transactional widget as though it works.
Use six independent capability dimensions: editable, previewable, persistable, renderable, interactive, and transferable. A button looking correct in a screenshot proves none of the last three. Supported modes are cloud, native WordPress, and connected transfer. A destination can be renderable but not locally editable under the current authority policy.
Proposed release groups are core content/layout; media/fonts/icons; templates/global resources; responsive/accessibility; publication/portability; native content/CMS; forms/integrations; agency/SaaS; advanced visual widgets; commerce/membership. Reconcile them against the actual repo before marking scope complete. Commerce and third-party widgets remain dependency-specific, not universally supported.
Acceptance: the feature ledger has no unexplained removal; every advertised capability maps to a fixture and a host-specific result. An old document with a currently uncertified widget round-trips without loss and receives a precise compatibility explanation.

4. Architecture decisions and service boundaries
4.1 Modular API, separate execution and serving
Use a modular monolith for account, workspace, site, page, permission, revision, release, connection, billing, and audit application logic. Keep these modules in one API deployable initially so related state changes can share a PostgreSQL transaction. Modules call public interfaces, not each other's internal tables arbitrarily.
Separate the editor application, API, background worker pools, public interactive runtime, and public static serving. Those boundaries reflect different trust, availability, and resource requirements. They do not require a microservice per feature.
Editing host
  Shared editor -> Cloud adapter -> Modular API -> PostgreSQL
  Shared editor -> WP adapter -> Local PHP API -> WP storage

Execution
  API transaction -> Operation + immutable input + outbox
  Dispatcher -> Redis-backed BullMQ -> Worker pool
  Worker -> persisted step / destination receipt / next outbox

Public serving
  Visitor -> CDN / serving origin -> immutable release
  Visitor -> WordPress / PHP -> active local document + assets

Optional event distribution
  Domain event outbox -> Kafka -> independent projections

RabbitMQ is an alternative task transport if requirements justify it; do not create a Kafka → RabbitMQ → BullMQ chain. A durable workflow engine can replace an overly costly custom orchestration layer later, but do not operate two competing workflow authorities for the same command.
4.3 Dependency budget
For each synchronous endpoint, name required dependencies. Save should not synchronously require Kafka, email, an analytics service, or an optional template provider. Public static reads should not require the editor database or queue, including on a cold CDN cache. Dependencies that enforce access or prevent known malicious serving are not optional simply to improve an availability chart.
Each new component needs an owner, security boundary, capacity budget, failure behavior, operating cost, upgrade plan, and exit strategy. Reject components that add names without solving a measured requirement.

Dynamic forms, authenticated pages and live search are separate runtime paths and must have their own dependency budgets. Public static availability does not imply that an unavailable form receiver can truthfully accept a submission.
A synchronous cache lookup may be bypassed only when its data is rebuildable and source fallback is bounded. Authorization, resource reservation and privacy revocation are not optional dependencies to discard for a faster benchmark. When a hot path exceeds budget, inspect its trace and allocation/query profiles before adding a new distributed service.
4.5 Write ownership register
The accounts module owns membership and account lifecycle; pages owns draft heads and page revisions; media owns asset state and pins; publishing owns release intent and workflow; the activation boundary owns the active serving selection; connections owns remote credentials and negotiated capabilities; billing owns reservations/settlement; privacy owns suppression state. Modules may join reads through reviewed queries, but writes to another module's state go through its application operation within a shared transaction when appropriate.
Use an explicit transaction context rather than starting unrelated nested transactions inside each service. A save-page-draft operation can call validation and authorization collaborators, but only its persistence boundary decides the commit. Avoid a remote authorization service in the initial save path: the selected modular API can enforce policy in the same database context.

7.3 Capacity and cost model
Estimate active worker slots as arrival rate × mean processing duration ÷ target utilization, then validate with p95/p99 service time, bursts, retries, and dependency limits. Budget database connections across maximum API/worker replicas plus migration/recovery reserves. A queue does not create CPU or provider capacity.
Track cost per successful publish, per active editing site, per GiB stored/delivered, and per 1,000 form submissions. Include CDN egress, database storage/IO, retained artifacts, Redis, compute, logs/traces, backups, email, Kafka if enabled, and human operating effort. No currency estimate is asserted without provider/region/traffic choices and current pricing.
Set account limits and global high-water admission. Protect already-accepted work, saved content, rollback, and export from optional AI or bulk-import consumption. Reference load tests must include one deliberately noisy tenant and show that unrelated tenants retain their adopted objectives.

For a 500 ms draft request, an initial diagnostic allocation is 30 ms admission/routing, 50 ms authentication/scope, 80 ms decoding/validation/hash, 180 ms database/commit, 30 ms response, and 130 ms headroom. A synchronous replication policy can consume more of the commit budget and must be measured rather than disabled to pass the benchmark.
7.5 Browser, database and storage envelopes
Initial browser controls: 100 undo command groups or 20 MiB of serialized inverse-command payload, whichever comes first; a 50 MiB local recovery budget per signed-in account subject to actual browser quota; no unbounded thumbnails or Monaco instances retained after editor navigation. Warn before evicting an unsent local recovery copy and offer export. Browser quota loss or permission revocation can still remove local persistence; host-saved is the only host durability claim.
Reference shell transfer budget: 300 KiB compressed initial application JavaScript plus 75 KiB CSS, measured separately from optional widgets, fonts and media. This is a proposed optimization target, not a promise that the existing editor can immediately meet it. A basic static published page should require no client JavaScript for reading content; cap first-party interaction JavaScript at 50 KiB compressed for the reference navigation/form fixture. Track total transfer and CPU separately because compression does not eliminate parsing/execution cost.
At 50 full-document saves/second and 250 KiB each, incoming document payload is about 12.2 MiB/second. If every write runs continuously for 24 hours and each creates a retained full snapshot, raw snapshot input is about 1.01 TiB/day before compression, indexes, replication, and backups. This is arithmetic under the benchmark's sustained-load assumption, not a forecast. Capacity planning must model duty cycle, document-size distribution, revision retention and object/WAL amplification. Do not retain every autosave forever by accident.
For the initial durable-save model, retain every accepted snapshot through a bounded recovery window, coalesce exposed autosave history after that window, and pin manual/release/held revisions. Preserve mutation receipts through their retry horizon even when an unpinned historical snapshot ages out. A repeated old mutation may return its receipt but cannot promise that an expired historical body remains downloadable. Checkpoints/deltas are an optimization only after replay, pruning and restore tests prove that no required base can be removed.
8. Shared editor and host-adapter implementation
8.1 Extract without duplicating the product
First wrap the existing load/save/media/revision/publish functions behind a CloudEditorAdapter. Keep the visible UI and existing document reader stable. Extract the canvas, selection, layer tree, inspector, command history, responsive controls, and widget registry incrementally. Each extraction runs the same browser fixtures before and after. Add a test adapter early and the WordPress adapter once the contract is stable.
The editor receives a host adapter, initial resource identity, capability snapshot, locale, and navigation callbacks. It does not discover a cloud API hostname itself. The host owns authentication, account routing, media selection, external links, and environment-specific error recovery. Capabilities influence UI availability but never replace server authorization.
8.2 Contract vocabulary
A typed adapter should expose loadPage, savePageDraft, uploadMedia, listRevisions, restoreRevisionToDraft, publishPage, getOperation, getCapabilities, and checkPermission. Requests accept cancellation signals where meaningful; cancelling the browser request does not prove the server cancelled an effect. Use a documented error union: unauthenticated, forbidden, validation, stale revision, authority conflict, unsupported capability, quota/admission failure, unavailable dependency, and uncertain external outcome.
A save carries page ID, expected revision, authority epoch, mutation ID, schema version, and the bounded document. A successful response contains persisted revision, accepted mutation ID, normalized document hash, and server acceptance time. On client retry after a lost response, the same mutation ID returns the original receipt if the request matches. A different body with that ID is a conflict.
Keep server drafts/revisions distinct from browser selection and history. Normalize node lookup and subscribe panels to the slices they need. Transient pointer motion must not serialize the whole document on every event. Use commands such as insert-node, move-node, edit-text, change-style, and update-binding with grouped undo transactions. Do not introduce CRDTs until simultaneous multi-writer semantics, permission changes, and offline merge are separately specified.
8.3 Save, offline, and recovery states
The UI distinguishes unsaved changes, local recovery copy, save in progress, host saved, conflict, and unavailable. Coalesce autosaves while retaining the latest unsent change. Never allow an old response to mark a newer document saved. Reconnect must reload the current authority/revision before submitting pending writes.
Use a bounded IndexedDB recovery journal scoped by account/workspace/site/page. Provide export and recovery after a crash; define retention, logout handling, shared-device behavior, and consent where needed. Do not treat browser storage as durable host persistence. Full offline WordPress editing is not automatically promised: core independence from ForgeStudio cloud means WordPress remains reachable locally, not that all browsers work without any host connection.
On conflict, preserve both versions and show a comparison or fork. Explicit replacement requires permission and a current precondition. The editor must not silently decide that whichever request arrived last is authoritative.
8.4 Accessibility and interaction
Keyboard alternatives to drag/drop, focus management, named controls, announced save/conflict status, contrast, reduced-motion behavior, and readable validation are required in the core editor. Test screen-reader journeys and keyboard-only operation, not only automated checks. Target WCAG 2.2 AA for the editor and supported first-party templates, with a declared evaluation scope. Do not claim every user-created website automatically conforms. [S29]
8.5 Editor state, subscriptions and rendering algorithm
Use two stores. The document store owns immutable node records, roots, page metadata, resource references, a local revision sequence and indexes. The session store owns selection, hover, drag preview, viewport, zoom, open panels and temporary text-input composition. Browser history owns grouped undo/redo commands; host state owns saved revision and authority. Do not copy these into one giant React context value.
A node inspector subscribes to its selected node and referenced tokens. The layer panel subscribes to structural changes and labels, not all style keystrokes. A canvas node subscribes to its own record plus relevant inherited styles/resource versions. Use stable immutable snapshots and selector-aware subscriptions. React documents the snapshot identity and subscription rules for useSyncExternalStore; simply returning a fresh object for every read is incorrect. [V4-S01]
For update-node-style, validate the local command, replace the target record using structural sharing, increment the local sequence, update affected indexes, append one grouped inverse command, then notify affected subscribers. Copying a plain object containing 5,000 node entries still has cost even when nested records are shared; profile it. Use a measured selector store or persistent structure if that copy is a real bottleneck, rather than claiming every operation is O(1).
During drag, read geometry in a bounded measurement phase, update a lightweight overlay through requestAnimationFrame, and commit one structural move-node command on drop. Do not write the draft, recompute every style or create 60 undo records per second. Keyboard move/reparent commands use the same domain command validator. Reject reparenting into a descendant or creating an invalid child type.
Virtualize long layer and asset lists first. Do not blindly unmount offscreen canvas layout: it can change browser flow, sticky positioning, measurements, selection, printing and accessibility. Canvas containment or deferred preview rendering needs fixture-specific correctness tests. Keep text entry, IME composition and selection urgent; defer optional search results and preview analysis. React transitions do not turn synchronous CPU work into a background thread and cannot control text input updates. [V4-S02]
8.6 Browser document worker contract
Use a dedicated browser worker for measured CPU-heavy validation, migration, dependency analysis, canonical hashing and export preparation. It cannot manipulate the DOM. Give every request requestId, pageId, baseLocalSequence, schemaVersion, task, and a bounded payload. Every response echoes identity and sequence. Discard stale results; a result for sequence 20 cannot mark sequence 24 validated or saved.
Initialize a worker replica once, then send bounded command batches or checkpoints where profiling justifies it. Sending a full 2 MiB document on every pointer event merely relocates CPU and adds copying. Transfer byte buffers when ownership semantics allow, measure structured-clone overhead, and recover a dead worker from the latest authoritative browser state. Keep a chunked bounded fallback for unsupported worker startup rather than freezing the page. Breaking long tasks and moving appropriate work off the main thread are browser-performance mechanisms, not a substitute for reducing total work. [V4-S03]
8.7 Save coordinator: the exact race policy
Maintain localSequence, inflightSequence, persistedSequence, hostRevision, authorityEpoch, and the current mutation record. There is at most one in-flight save per browser page session. New changes while saving are coalesced into the latest unsent candidate; they are not silently discarded. The mutation ID and exact candidate hash are persisted in local recovery before transmission when local storage is available.
On acknowledgement for sequence n, advance hostRevision and persistedSequence to that accepted state only. Do not overwrite newer local content n+1..m with response content for n. A server-normalized change is applied only if it still matches the submitted state; otherwise perform a controlled rebase or pause for comparison. When a response is lost, retry the same mutation ID/body/precondition; do not invent a new mutation and overwrite with stale content.
If another tab changes the host revision, receive the hint through BroadcastChannel where available but rely on the server precondition for correctness. A 409 DRAFT_REVISION_CONFLICT response freezes automatic writes, keeps local work and loads the competing version for comparison. A 401 stops automatic saves and presents reauthentication without deleting the unsent draft. A 403 or authority change stops retries; local export remains subject to the application's content-access policy. The UI marks 'Saved' only when no local sequence is newer than the persisted sequence.
A tab close handler is best-effort and must not be the only save mechanism. Do not call sendBeacon and assume the host committed. Reopening the editor offers an unsent recovery copy separately from the current host document.
9. Portable documents, schema evolution, and reproducible hashes
9.1 Canonical content model
A document holds schemaVersion, logical page ID, root node IDs, normalized nodes, typed widget settings, child IDs, responsive overrides, design-token references, media references, and allowed extension data. Site-level navigation, headers/footers, templates, typography tokens, and reusable components have separate immutable revisions. A release pins them together.
Keep schema version, content revision, renderer version, widget version, release identity, connection generation, and authority epoch separate. Cloud/WordPress internal database IDs are mapped at the adapter/protocol boundary. Carry potentially large external numeric identifiers as strings rather than assuming every JavaScript/PHP integer representation agrees.
Use one shared JSON Schema vocabulary that both runtime implementations actually validate. Generated TypeScript types are not runtime validation, and a JavaScript validator is not a PHP validator. Allow unknown content only in explicit bounded preservation fields or read-only legacy storage; never pass unknown fields directly into HTML attributes, executable code, or persistence authorization.
9.2 Validation and migrations
Reject duplicate IDs, cycles, orphan references, unsupported writable schemas, malformed widget settings, unsafe URL schemes, oversized strings, too many nodes, excessive nesting, unbounded queries, and missing/unowned assets. Validate twice: fast client feedback and authoritative host validation. Error responses identify the node/field and preserve the user's source.
Migration is a deterministic function from one known schema to another with a preserved original and report. Test forward conversions, replaying a migration, skipped versions, and unsupported future schemas. Never normalize away unknown widget data to make validation appear successful. Read-only display/export is safer than destructive conversion. Pin migrations to versions and record which migration produced the stored result.
9.3 Cross-language canonicalization
A TypeScript JSON.stringify output and PHP json_encode output must not be assumed byte-identical. Select a canonicalization specification, finite-number constraints, string handling, and sorting rules; test both implementations using the same vectors. RFC 8785 provides a JSON canonicalization scheme suitable for hashable representations. It does not perform arbitrary Unicode normalization for the application. [S26]
Define a canonical document digest separately from the digest of raw received webhook bytes. For document comparison use canonical content plus schema identity; for HMAC authenticate exactly the agreed raw envelope. Reject duplicate JSON object keys at untrusted signed-document ingestion where ambiguity could produce different interpretations. Use bounded numeric ranges and explicit decimal-string/unit rules for values where cross-language number formatting matters.
A release build fingerprint includes document/resource hashes, renderer and widget versions, relevant feature/configuration versions, locale, and resolved assets. Store timestamps and operation IDs in release metadata outside deterministic artifact inputs where possible. Dynamic content is marked as runtime-resolved rather than pretending its current HTML is reproducible forever.
9.4 Concrete document boundary and validator pipeline
The companion pack supplies a reference contracts/page-document.schema.json and fixtures. The closed core envelope contains schemaVersion, pageId, locale, rootIds, nodes and breakpoints; resource bindings are carried by the separately versioned release/resource contracts. Node records contain stable ID, widget type/version, child IDs, settings and style values. Core settings use per-widget closed schemas; an unsupported widget is stored only in a bounded opaque preservation field with an explicit unsupported marker, never executed.
Validation order: limit received and decompressed bytes; decode strict UTF-8 and reject ambiguous duplicate object keys; validate structural schema; verify map-key/node-ID agreement; enforce one parent per ordinary tree node and root membership; detect cycles/orphans with an iterative traversal; validate allowed widget children; resolve token/component graph without cycles; verify asset/resource ownership; validate route and runtime binding semantics. Report errors by stable node ID and field path, capped initially at 100 useful errors. Extra errors are counted, not an unbounded response.
Use opaque IDs as strings. Version counters exposed to JavaScript remain bounded safe integers or decimal strings, selected consistently. Numeric CSS values use a finite bounded number and an explicit unit enum; arbitrary CSS strings are a separate privileged policy, not an escape hatch in every property. Distinguish missing override from explicit reset. The schema alone cannot prove ownership, graph acyclicity, safety of all URLs or renderer parity; application validators and database constraints complete that contract.
Document fingerprints use a domain-separated SHA-256 digest of the adopted canonical representation, schema identity and relevant resource dependencies. RFC 8785 supplies canonicalization rules but does not normalize arbitrary Unicode or remove the need for a compatible number model. [V4-S04] A webhook signature instead authenticates the precise received signed bytes. Never reconstruct those bytes by serializing parsed JSON.
A portable export manifest includes format version, page/resource mappings, asset paths/checksums/byte sizes, widget requirements, source-authority metadata for information only, and a compatibility report. Imported authority or account fields cannot grant access: the receiving host creates fresh ownership from its authenticated context.
10. Widget system, rendering, assets, and page semantics
10.1 Widget contract
Each first-party widget owns a settings schema, defaults, inspector UI, editor preview, static render behavior, PHP render behavior where supported, optional browser runtime, accessibility behavior, migration functions, and fixtures. Its manifest declares required capabilities, script/style dependencies, dynamic data needs, allowed child types, and supported host modes.
Use common style semantics: breakpoint ordering, base inheritance, explicit override versus unset, units, hover/focus states, container behavior, specificity, and token resolution. A pixel-identical screenshot alone is insufficient; assert text, headings, links, routes, form behavior, keyboard interaction, and absence of editor code in public output.
Separate widget editor code from its public runtime. Emit only the scripts/styles actually used by a page or release. Define explicit module execution and hydration contracts to avoid duplicate event handlers after navigation or preview reload. Error boundaries isolate a failing optional widget where safe; missing critical content should block publication, not disappear silently.
10.2 Static and dynamic output
Cloud publication compiles HTML/CSS and small necessary browser runtime modules. WordPress uses PHP in its supported lifecycle. Dynamic widgets resolve through their host's runtime APIs and have independent timeout/cache/privacy contracts. A template that needs WooCommerce must report that dependency; it is not automatically a standalone commerce implementation.
Never mix personalized fragments into a public shared cache. Cache keys identify tenant/site, active release, locale, renderer/configuration dependencies, and any deliberately supported variation. Private previews are authenticated or protected by appropriately revocable access; noindex is not an access-control mechanism.
10.3 Media lifecycle and portability
Use initiate-upload, upload bytes to quarantine, verify completion/ownership/checksum, inspect media, produce bounded variants, and mark ready. Enforce extension/content-type consistency, decoded-pixel limits, decompression limits, resource budgets, and nonexecutable storage. Reject or sanitize risky formats under an explicit policy. Do not hand raw SVG or HTML the same public trust as a safe bitmap.
Assets use logical IDs mapped to host storage, not hardcoded expiring URLs in saved documents. Connected publishing copies required assets into WordPress and remaps IDs and internal links. Record checksum, byte count, actual attachment ID, license/provenance where supplied, and failed items. Deduplicate within allowed ownership scope; do not reveal that another tenant owns a matching private asset.
Deletion is delayed: mark eligible, acquire a deletion lease, recheck references and holds, then delete and record a receipt. A concurrent publication may add a pin, so garbage collection must share an enforceable reference protocol with publication. Retain active, in-flight, rollback-retained and legally held references. Abandoned multipart uploads and failed temporary files need separate bounded cleanup.
10.4 Widget implementation checklist and rich-text behavior
A completed widget is not one TSX file. Its directory contains settings schema, default settings, inspector, editor preview, pure rendering inputs, runtime initialization/disposal when interactive, PHP counterpart where supported, migration functions, fixtures and a capability manifest. Separate browser editor imports from public runtime exports so tree shaking is not the only barrier to accidental editor shipping.
Rich text uses a structured, versioned inline/block model with defined headings, links, lists, emphasis and allowed marks. Paste imports sanitize and normalize into that model; they do not store uncontrolled HTML as a universal content format. Preserve IME composition, grapheme-aware selection and undo grouping. Link and mark editing are actual domain commands. HTML/source editing, where sold, remains a separately permissioned escape hatch with preview isolation and output policy.
Specify runtime mount(root, settings, context) and dispose() behavior for first-party interactive widgets. Mount once per node/render generation, remove event listeners/timers on disposal, abort stale requests, and handle reduced motion. Duplicate mounts after preview navigation must not submit a form twice. Runtime settings never contain provider credentials.
10.5 Media and archive limits chosen for the reference profile
Initial proposed safe defaults: bitmap upload <= 20 MiB, decoded image <= 25 million pixels, longest side <= 12,000 pixels, worker RSS cap 512 MiB and image-processing wall time <= 30 seconds. Animated input is rejected in the first bitmap processor rather than decoded with an unbounded frame count; GIF/WebP animation and video need a distinct reviewed profile. A compressed file's byte size is not its decoded-memory requirement. Exceeding a limit produces a typed rejection, not a partly ready asset.
Imports initially allow 100 MiB compressed, <= 500 MiB expanded, <= 2,000 entries, <= 20 directory levels and an expansion ratio <= 20, all enforced while streaming. Stop when any bound is crossed. Reject path traversal, absolute paths, symlinks, duplicate normalized paths and nested archives in the core import format. These values are candidate policies to test with real parsers; lower them if host capability requires. Do not silently lift them when one test fails.
SVG defaults to disabled raw upload; a reviewed sanitizer or isolated rasterizer may enable a supported subset. Font uploads require MIME/signature validation, a declared supported format and user-confirmed licensing; do not redistribute platform font files. Media metadata records processing version and input checksum so changed optimization settings invalidate stale variants.
10.6 Collection race: a concrete pin protocol
Publication and deletion share one asset-state protocol. A release transaction may create a pin only while the asset is READY and not deletion-claimed. Cleanup atomically changes an unpinned eligible asset from READY to DELETE_PENDING and records a generation. A concurrent pin and delete claim lock or conditionally update the same asset row; exactly one compatible transition wins. Once DELETE_PENDING, new publication must reuse another ready asset or wait for an authorized cancellation of deletion, never attach a pin blindly.
The external object deletion runs outside the SQL transaction. Its receipt is persisted idempotently; a worker crash resumes by checking object existence/version and deletion generation. A temporary grace delay helps recovery but is not the synchronization mechanism. Provider object version IDs and holds are handled explicitly; deleting a current key alone may leave older readable versions. WordPress local attachment deletion follows the corresponding local pin policy and respects user/site permissions.

11.2 Tenant context and RLS
Derive tenant context from verified membership and resource ownership, not a body/header field alone. Propagate it through HTTP handlers, repositories, workers, exports, caches, object keys, search projections, metrics access, and support tools. Composite keys/foreign keys prevent attaching a resource to a different tenant even when application validation is missed.
PostgreSQL row-level security is defense in depth. Use a non-owner application role without BYPASSRLS and explicitly test policy coverage. Table owners normally bypass RLS unless forced; privileged roles and other mechanisms still require review. Set transaction-local scope using the same connection that executes the query and test pool reuse. [S09]
The migration role, scoped application role, release activation identity, cleanup identity, and backup role have separate privileges. Views, raw SQL, administrative endpoints, and background jobs must not become accidental bypass paths. Never use a customer-supplied queue workspace ID as proof of permission. [S05]
11.3 Concurrency and durability
Drafts use revision preconditions, not last-write-wins. Short transactions enforce uniqueness, quotas, and operation acceptance. External requests/builds run outside database transactions. Retry serialization/deadlock errors only with bounded idempotent operations.
Choose the actual managed PostgreSQL replication/commit policy before promising acknowledged-write durability. Synchronous replication can strengthen commit guarantees but affects availability/latency when required replicas are unavailable; asynchronous replication can lose recent data on failover. Measure the selected policy and state its failure scope. [S10]
Operate PITR, monitored backup completion, WAL/storage headroom, replication lag, query timeouts, lock-wait alerts, connection pooling, and index/migration observability. Use online expand/backfill/verify/switch/contract migrations, not startup DDL. A code rollback is allowed only across a schema compatibility window; destructive migration reversal is not assumed.

11.5 Save transaction and lost-response handling
The core API uses an explicit expectedRevision field in its draft-save command. The server first authenticates and validates request bounds, then validates the document shape and computes its canonical digest outside the short write transaction. Mutable ownership, policy, references and authority are rechecked at the commit boundary. A validation cache cannot replace this recheck.
Within one transaction: claim the tenant/action/idempotency key through a unique constraint; if an existing completed identical request is found, return its receipt after current read authorization without repeating the write. A different request hash using the key returns IDEMPOTENCY_KEY_REUSED. For a new request, verify the expected head and authority, insert an immutable revision, pin required ready assets/resources, conditionally advance the head, write the mutation receipt and audit event, and commit. If the CAS affects no row, roll back all new records and return DRAFT_REVISION_CONFLICT. The losing writer's submitted document remains in browser recovery, not as an accidentally authoritative revision.
A representative statement inside that transaction is:
UPDATE page_drafts
SET head_revision_id = $1,
    revision_counter = revision_counter + 1,
    updated_at = CURRENT_TIMESTAMP
WHERE workspace_id = $2
  AND page_id = $3
  AND revision_counter = $4
  AND authority_epoch = $5
RETURNING head_revision_id, revision_counter;

This is a parameterized reference pattern, not a complete migration or standalone authorization system. The surrounding transaction, unique request receipt, correct same-page revision FK and reference/policy checks are mandatory. Do not interpolate identifiers or assume WHERE workspace_id = suppliedHeader verifies membership.
If the transaction committed but the client lost the response, the same request returns the original receipt even though the head has advanced since the original expectedRevision. This replay does not mutate the new head. A revoked actor does not regain access to the receipt just by retaining an idempotency key. Define receipt retention as longer than the maximum supported client retry horizon; unlimited historical replay is not promised.
11.6 Consistent release input without a long build transaction
In a short consistent-read transaction, pin the chosen page heads, global resources, routes, form schemas and build configuration into an immutable release manifest. Lock only the rows necessary for approval/authority and coherent version selection. End the transaction before compiling or transferring. Later changes create another draft/release rather than changing pinned inputs. Approval binds this manifest hash and destination configuration, not a mutable site ID alone.
Use a consistent database snapshot or validate all selected versions again before committing the manifest. A series of independent reads without a coherent snapshot can accidentally combine an old route map with new page references. Never lock the whole site for the duration of a 100-page build.
11.7 Runtime database safeguards
Set named read/write/worker connection pools, bounded acquire/statement/lock timeouts and a connection ceiling across maximum replicas. A proposed hot-write lock timeout is 250 ms with limited retry, statement deadline 1 second and no retry beyond the endpoint deadline; adjust only after measuring the replication/storage profile. Slow background queries use a separate pool and budget. Query-plan evidence includes realistic row counts and production-shaped selectivity, not only an empty development database.
Test table-owner/RLS behavior, transaction-local context and pooled connection reuse against the selected provider/pooler. PostgreSQL documents that row-security protection depends on roles and policy configuration. [V4-S05] Treat application-scope policy as defense against developer mistakes as well as malicious input; a database superuser is outside the ordinary runtime trust boundary.
12. Tenant isolation, identity, and privileged access
12.1 Identity lifecycle
Implement verified signup, login, secure session handling, explicit logout, session/device revocation, password reset, optional external identity linking, invitation acceptance, account recovery, and account closure. Rate-limit sensitive flows with a conservative fallback when controls are unavailable. Do not leak whether an email belongs to a private account through recovery responses.
Use secure host-scoped cookies, appropriate SameSite and CSRF protection, and strong reauthentication for high-risk changes. A browser-accessible API token is not a substitute for a secure session design. Never store recoverable passwords. MFA is required for platform administrators and proposed for workspace owners; recovery must not become a weaker bypass.
12.2 Roles and decisions
Suggested roles: account owner, workspace administrator, designer, content editor, reviewer, publisher, billing administrator, and viewer. Treat these as capability bundles, not hardcoded bypasses. In the default production policy, design editing does not automatically grant production publish; an owner may grant it deliberately. Platform administrators are not ordinary workspace users with an invisible universal permission.
Approve changes against exact candidate hash, site/environment/destination, authority epoch, and relevant configuration. Changes invalidate approval. Decide self-approval and owner override policy explicitly; audit all overrides. Recheck current permission and connection scope before critical queued effects. Define the revocation boundary honestly: a remote effect already authorized/committed before revocation may complete; the UI cannot retroactively cancel it.
12.3 Support access
Support sees safe operational metadata by default. Private content or tenant mutation requires time-limited, tenant-scoped elevation with ticket/reason, approver where required, explicit duration, and durable audit. Exported support bundles are redacted and consented. Ban unlogged “login as customer” endpoints and direct production database edits as normal support practice.
12.4 Isolation acceptance
Test cross-tenant reads/writes on documents, revisions, jobs, file download URLs, assets, templates, forms, webhooks, billing, search, exports, domain bindings, and support APIs. Include guessed valid IDs, stale membership caches, manipulated queue payloads, cross-tenant object references, and reused connection-pool sessions. Hash-like IDs are not authorization controls. [S05]
12.5 Early tenancy bootstrap and capability policy
Account/workspace/membership storage must exist before tenant-facing page, asset, operation or connection writes are exposed. This corrects the earlier backlog order, where the full account-boundary package appeared after several dependent features. A later SaaS phase can add invoicing and agency conveniences; it must not postpone foundational tenant isolation.
The default capability map separates content edit, design edit, staging publish, production publish, approval, rollback, connection management, member management, billing, export and deletion. Designers do not inherit production-publish rights by naming convention. A content editor can modify only allowed fields; the server validates the changed-field policy, not merely a disabled inspector control. Bulk document replacement must not bypass field-level restrictions.
Define the revocation linearization point. Critical writes evaluate policy within their commit/activation protocol. A revocation that commits afterward cannot undo an already committed effect. Where strict ordering is required, policy mutation and critical effect authorization use a shared policy-generation guard; do not serialize every ordinary keystroke on a global workspace mutex. Scheduled jobs specify an approved service policy and recheck whether their creator, schedule and connection remain authorized.
Invite records bind recipient, workspace, role, expiry, single-use identity and issuing actor. Role changes and account transfer require reauthentication and invalidate affected outstanding invitations. Separate agency branding from universal agency access to every client workspace.
13. Browser, preview, and public-content trust boundaries
13.1 Separate platform and customer content
Host account/editor traffic and untrusted customer sites on different registrable domains where practical. Use host-only cookies and never broad parent-domain session cookies. Isolate uploads according to MIME/content trust. Do not rely on subdomain naming alone to prevent cookie, service-worker, or storage surprises; test the actual origin and path rules.
Editor preview for arbitrary custom HTML/scripts runs in a separate sandboxed context with a minimal validated message protocol. Check message origin/source where meaningful and capability/token binding for opaque sandbox origins. Do not grant both same-origin privileged access and unrestricted scripts to untrusted content. Editor code must not evaluate customer code in its own origin.
13.2 Code and third-party dependency policy
No arbitrary PHP on the platform. No tenant-provided npm installation during publication. No access to the host Docker socket. First-party rendering uses known widget implementations and validated configuration. A privileged custom-script feature requires separate consent, security policy, isolation, and published limitations. Third-party scripts on a WordPress public page inherit that site's origin risks; the plugin cannot promise to neutralize every malicious script installed by the host administrator.
Use CSP and safe rendering/escaping as layers, not as a replacement for input validation. Rich-text, URLs, SVG, CSS imports, embedded frames and link targets have explicit policies. Template imports use the same validation as user input. Sanitizer/renderer version changes may require a controlled security re-render, with a report rather than silently changing historical source.
13.3 Domain and cache ownership
Domain binding requires proof of control, uniqueness, normalized hostnames, and explicit account/site association. Removing a binding revokes its ownership claim and schedules serving/certificate cleanup; stale DNS alone must not allow another tenant to inherit the old content. Reverify relevant ownership changes and rate-limit certificate operations.
Preview access must not enter a public cache. Cache keys and routing must not trust an arbitrary Host/header combination. Test encoded paths, query normalization, forwarded-host trust, redirects, and cache poisoning. Long-lived public assets contain no secrets; signed private URLs have documented expiry/revocation limits. An already downloaded file cannot be recalled.

A publish request authenticates the actor, checks current scope/approval/quota/authority, and pins exact page/shared-resource/route revisions. In one short transaction it creates or reuses the logical operation, release intent, outbox and audit record. Return accepted only after commit. Builds and remote calls occur after that transaction.

14.3 Meaning of a successful publication
Success requires retained immutable input, verified artifacts/assets, authorized destination activation with a durable receipt, and the declared live-verification checks. A 200 response with wrong content, a stored local publishedData flag or a completed queue job is insufficient. Store expected and observed release/hash/generation.
For managed static hosting, verify the serving manifest and at least the home route plus all changed critical routes within a bounded check policy. Large releases verify route/asset references statically and sample public delivery according to a recorded coverage policy; do not claim every remote edge was tested. For WordPress, read the authenticated operation receipt and current managed page state, then check the actual public route and native side effects required by that host contract.
If optional email or analytics fails after publication, retain SUCCEEDED and expose that downstream failure separately. If mandatory local evidence cannot be persisted after remote success, leave the recoverable intent and reconcile; do not return an invented clean result.
14.4 Ordered activation and stale-worker prevention
Default ordering is per site/environment/destination. Parallel compilation is allowed. The activation boundary accepts only the next authorized predecessor/generation and current authority epoch. A newer approved operation may explicitly supersede an older unactivated one; the policy is recorded before either effect can begin. A stale worker cannot fetch a new precondition and silently reinterpret its old request as the next publication.
An approval binds the complete input manifest hash, target environment/destination, authority epoch, relevant rendering/security configuration and allowed actor/override policy. Altering any bound input requires a new approval. Owner overrides are explicit audited decisions, not a query that finds any historical APPROVED row.
Cancel and retry commands require the current operation version and permission. Browser AbortController, a killed pod or an expired lease does not prove remote cancellation. The control layer can stop future steps; an already uncertain effect requires receipt reconciliation. Restoring a draft changes only its head; live rollback activates a retained safe release with a fresh destination precondition.
14.5 Activation receipt and effect intent
Before activation, persist an effect intent containing operation/effect ID, target identity, expected generation, epoch, candidate hash and request configuration. Queue payloads carry references rather than secrets. The receipt contains operationId, destinationId/installationId/blogId, releaseId, inputHash, previousGeneration, newGeneration, authorityEpoch, appliedAt and actual resource mapping. Receipt authentication comes from the verified channel/protocol, not merely valid JSON.
The destination must either return the same receipt for the same idempotent effect or reject a conflicting payload. It must not overwrite the receipt with a later retry. Preserve receipt identity in the active manifest/local WordPress commit boundary so lost source responses can be reconciled. Where a provider lacks these primitives, declare a weaker supported operation and a manual uncertainty path rather than advertising universal exactly-once effects.
The companion state contract validates basic publication invariants, but only real database and destination concurrency tests establish the implementation's effect boundary.
15. Serving plane and immutable release activation
15.1 Serving independent from editing
Place built files under immutable release/content-addressed keys. Store a per-site/environment serving manifest pointing to the active release, with a generation and previous-release reference. The serving origin loads this from an independently available serving store; a cold CDN miss must not query the editing database. Public route maps, locale mappings, redirects, and immutable asset references belong to the serving release contract.
Only a tightly scoped activation identity may update the active manifest. Builders can create staging objects but cannot select the live release. The manifest store must support an atomic conditional update or an equivalent tested single-writer protocol. Amazon S3 supports conditional writes; other S3-compatible products must demonstrate the required semantics rather than inherit the claim by name. [S28]
Do not treat an ETag as a universal cryptographic content hash. Store a separate verified digest where needed. If a manifest update succeeds and the cloud database acknowledgement fails, read the manifest's operation/receipt identity during reconciliation. Two unrelated stores are not one transaction.
15.2 Cache and propagation contract
Activation is authoritative at the manifest update; CDN convergence is not globally simultaneous. Retain prior assets long enough that older cached HTML still resolves. Prefer immutable asset URLs and bounded manifest/HTML TTLs with supported invalidation. Measure origin selection and representative edge observations separately. Never claim every edge was updated at the exact same instant.
Define cache keys for site, host, path, locale, encoding and supported variants. Invalid or unknown hosts fail safely. Separate published public objects from private originals and preview artifacts. Object storage listing, presigned URLs, and debugging endpoints must not expose unrelated tenants.
15.3 Emergency controls
Provide independent pause-new-publications, pause-outbound-effects, disable-optional-widget, and site-suspension controls. A known compromised or legally restricted site may require a serving-plane denial even while the editor is unavailable. Scope and protect that control; it must not become an unaudited universal content deletion switch.
Optional multi-CDN or multi-origin failover requires certificate/domain validation, privacy/cache equivalence, and rehearsed routing. It is not a launch requirement unless the adopted availability model needs it. Retaining immutable output is necessary but not sufficient if DNS, certificates, routing, or the origin itself fails.
15.4 Incremental build graph: the primary publication speed feature
Store dependencies as edges from each page to the exact global components, style tokens, fonts, widget runtime versions, media variants, routes, locale data, CMS snapshots and approved configuration it uses. Maintain reverse edges for invalidation. A change to one text node normally invalidates that page; a global header or font token invalidates every dependent page. Unknown/dynamic dependencies force the safe full-build path or an explicitly runtime-resolved boundary.
The build key is a digest of page revision, transitive resource fingerprints, compiler/renderer versions, asset variant checksums, locale and resolved configuration. Never reuse an output solely because its page ID or slug is unchanged. Keep caches tenant-scoped for private content and do not expose whether another tenant has the same asset or template.
Algorithm: freeze input manifest; compare dependency fingerprints to the previous verified release; calculate affected closure; reuse verified immutable output only for unchanged eligible nodes; compile affected pages under bounded concurrency; validate links/routes/asset references across the complete release; upload only missing verified objects; create a complete new release manifest; then activate through the same guard used by a full build. Reusing artifacts does not mean activating a partial manifest.
Changed detection must include deletion, renamed route, new renderer safety rules, sanitizer fixes, font changes, widget versions and secret-free integration configuration. Runtime-bound data uses explicit cache/invalidation semantics, not an accidental snapshot from the compiler's current time. Invalidating too much costs performance; invalidating too little publishes incorrect content. Correctness wins when the dependency graph is uncertain.
Acceptance compares full and incremental builds of the same pinned input for semantic content, route maps, selected widget/runtime assets and stable artifact hashes where byte-deterministic output is promised. Inject a global-token change, shared header change, asset replacement and page deletion; all affected pages must update. Cache corruption forces a verified rebuild, not trusted reuse.
15.5 Serving manifest structure and activation authority
A proposed serving record carries site/environment identity, installation or serving target, generation, authorityEpoch, operationId, releaseId, manifestHash, previous release reference and an applied timestamp. The release manifest maps normalized routes to immutable HTML, CSS and runtime objects. A host-binding record maps a verified hostname to a site/environment and is not derived from an arbitrary request header.
Conditional object replacement is one possible activation primitive; Amazon S3 documents If-Match/If-None-Match behavior, but another compatible store must be tested independently. [V4-S06] An ETag is a concurrency validator, not a universal SHA-256 digest. Use an explicit content digest for artifact integrity.
Do not give every build worker unrestricted permission to overwrite the active manifest. A scoped activation component enforces operation authorization, publication ordering, expected generation and current authority. It can be a worker role within the same codebase, not a new microservice. Its conditional write must be bound to the operation's authorized predecessor. A stale worker is not allowed to read the latest ETag and retry its old publication with that new precondition.
The serving origin reads verified host bindings and manifests from its own available store/cache. It serves a known active immutable release on ordinary optional-control failures, but handles security suspension and unknown-host errors through a separate protected policy. Test a cold origin and cold CDN with editing PostgreSQL, Redis and Kafka all unreachable.
15.6 Public cache policy and invalidation
Immutable public assets use long-lived content-addressed URLs. HTML and serving selection use short policy-controlled caching; a candidate maximum stale-serving window for ordinary publication is 30 seconds on the reference provider, measured separately from emergency takedown behavior. A purge request acknowledgement is not proof that every browser/edge discarded content. Report origin generation, purge receipt and representative edge checks separately.
Define whether query strings affect content. Marketing parameters that do not change output can be normalized out of the cache key; locale, authentication, preview tokens and supported content variations cannot be ignored. Never use a public cache for personalized HTML. Cookies should not be sent on static asset requests from the platform domain. Negative caching must not hide a newly activated route longer than the declared policy.
Do not delete old release assets merely after changing the manifest: old cached HTML, pinned rollbacks and downloads still reference them. Security revocation of a vulnerable runtime may require patched restoration or serving denial rather than exact historical rollback.
16. Native WordPress architecture and local execution
16.1 Real plugin, not a cloud wrapper
Ship a ZIP containing namespaced PHP, compiled shared-editor assets, core widget assets, required production PHP dependencies, translations, and a build manifest. No npm/Composer execution or customer-installed Node, Docker, PostgreSQL, Redis, Kafka, or Kubernetes is required. Core local editing, media, rendering, revisions, and publication must remain functional with ForgeStudio domains blocked.
Use WordPress-provided React where compatible with the support contract, or isolate a deliberately bundled runtime; never mix incompatible instances in the same component tree. Enqueue editor assets only on the editing screen. Public pages receive only necessary runtime modules and styles. Package/license/source availability must comply with the chosen distribution route, including WordPress.org rules where submitted. Document optional external services and telemetry. [S22]
WordPress's requirements page provides a reference hosting baseline, but ForgeStudio's support matrix is established by its own CI and real-host tests. Record exact WordPress/PHP/database versions, locale, permalink mode, theme, persistent-cache setting, multisite mode, and server limits for every certification run. [S21]
16.2 Native identity and document storage
Pages/posts own native identity, authorship, URL and publication status. Use registered metadata for bounded documents, with explicit schema, sanitization, capability checks, and intentionally configured revision support. Use the media library for local assets. Registered metadata alone does not automatically solve revision retention or publication activation. [S20]
Use small prefixed plugin tables for guarded page state, immutable release snapshots/receipts where needed, local operations, and deduplication. Use the actual blog-specific prefix and WordPress upgrade conventions. Keep plugin storage version separate from plugin version; upgrades are bounded and resumable. [S19]
Do not rely only on native revision retention for the active and rollback-required documents: a host may prune revisions. Pin/copy the required immutable snapshot in plugin-owned release storage and test with native revision pruning. Registered draft metadata and the active published snapshot are different resources. Always preserve a supported export path.
16.3 Publication atomicity: exact boundary
The first guarantee is atomic selection of the active plugin-rendered document and its asset manifest for one page, not an atomic change across all WordPress tables, hooks, themes, caches, menus, and pages.
Stage the immutable snapshot and verify assets first. Claim the operation with expected authority/revision. On a supported transactional database configuration, update the guarded page-state pointer and activation receipt together through one controlled connection/transaction, or use a tested atomic row update that embeds the necessary receipt identity. The renderer selects content from that committed pointer. Recovery reads that state if the HTTP response is lost.
Native post title, slug, publication status, navigation, external hooks and third-party caches can be additional side effects. Define their sequencing and reconciliation. For an existing published page, do not expose new native fields before the matching prepared content is available. For a first publication, complete staging before enabling the public route. Keep redirects/route compatibility where possible. If required native effects are incomplete, show a partial/reconciling outcome; do not claim full atomicity.
If the hosting configuration cannot provide the tested storage guarantees, report the limitation and disable unsupported atomic connected activation rather than silently using a weaker path. Whole-site atomic WordPress activation is a separate future manifest/router project.
16.4 Authentication, permissions, and compatibility
Local REST calls use WordPress authentication and nonce handling plus server-side capability checks. A WordPress nonce helps address CSRF but is not authorization and is not a single-use replay defense. Use actual operation IDs and durable deduplication for effects. [S17][S18]
Remote access can initially use an HTTPS Application Password tied to a dedicated least-privileged user, but plugin routes must also enforce connection-specific page/site/action scope. Host administrators can revoke credentials independently. Discover the actual REST URL through WordPress rather than hardcoding pretty permalinks. Support plain permalinks and network/subdirectory configurations in tests.
Offer theme-content mode and an explicit full-canvas template. Test classic/block themes, header/footer ownership, native content interactions, cache plugins, security plugins, media offload where declared, WooCommerce only where declared, and multisite per-blog scoping. Do not globally take over theme behavior.
16.5 Background work and diagnostics
Use a local durable PHP task store. Action Scheduler is the proposed library for imports, local preparation, retries, and upgrade batches, with a tested dependency/version integration. Its execution remains subject to WordPress request/runner opportunities and host limits. [S23][S24]
Save normal bounded drafts synchronously. Split larger jobs into restartable chunks with operation IDs and checkpoints. Show waiting/running/retrying/blocked state. Provide authenticated bounded continuation and documented WP-CLI/system-cron support where the host allows it. Do not promise exact-time scheduling on an arbitrary low-traffic site. Diagnose disabled cron, blocked loopbacks/HTTPS, task age, writable paths, memory, and execution limits. [S37]
Deactivation preserves data. Explicit uninstall deletion requires a documented policy and informed action. Preserve a safe native-content fallback for supported basic output; dynamic widgets may stop when their renderer is deactivated. An installation with local admin/root compromise is outside a claim of tamper-proof storage. Include safe-mode export and recovery instructions that do not require cloud access.
16.6 Concrete PHP responsibilities and local hot path
Proposed files: class-editor-screen.php registers/mounts the host; class-page-repository.php manages guarded draft identity; class-document-validator.php validates the shared schema/semantics; class-render-cache.php caches safe output; class-page-renderer.php selects and renders the active snapshot; class-release-repository.php pins immutable local release data; class-publish-controller.php validates/activates and returns receipts; class-operation-repository.php retains retry/deduplication state; class-cloud-connection.php owns local scope/revocation; class-background-runner.php performs bounded work; class-site-health.php reports actual capabilities.
Public render: determine current blog/post and supported template mode; read the small guarded page-state record; resolve the pinned snapshot and renderer version; use a cache key containing blog/post, active snapshot hash, locale and renderer/configuration versions; return stable HTML and enqueue only required assets. Dynamic fragments have separately declared user/cache contexts. Do not load draft JSON, revisions, connection credentials or the editor bundle on a public read.
WordPress transients can disappear before their expiry; they are caches, not operation or activation storage. [V4-S07] A cache miss rebuilds from durable local content with bounded work. Persistent object cache is optional. Use a local stampede-control method only where its atomicity is established; an ordinary get_transient followed by set_transient is not a distributed lock.
16.7 Local write and activation transaction sequence
The draft save rechecks native capability, connection authority where relevant, expected revision and content validation. Claim the mutation identity, create the immutable local snapshot, advance the same-page draft state and record the receipt in a supported local transactional boundary. Native metadata can expose the draft through WordPress APIs, but must not diverge into a second authoritative write head. Register synchronization behavior explicitly and diagnose external edits rather than overwriting them blindly.
For activation, verify staged assets first, then begin the short local transaction; check existing operation receipt; check expected active generation, authority and page scope; select the pinned prepared snapshot; conditionally update the page-state pointer; insert the immutable receipt; commit. Native status/slug/title reconciliation occurs under the declared per-page protocol, not an invented transaction across arbitrary hooks. On rollback or lost response, query the receipt and active pointer before retrying.
Use blog-specific prefixes and versioned upgrade routines as WordPress documents. [V4-S08] Detect unsupported table-engine/host behavior and disable only the stronger connected-activation guarantee with a clear explanation; do not silently weaken the contract. Local core storage/exports remain protected. Do not make users paste SQL manually to finish a normal installation.
16.8 Local jobs, updates and safe mode
Initial local batches aim for <= 5 seconds or <= 10 records per pass, whichever occurs first; actual PHP time/memory headroom can lower these bounds. Checkpoint before yielding and expose continuation through a capability-checked endpoint or CLI. WordPress cron and Action Scheduler remain dependent on execution opportunities under their supported runners. [V4-S09][V4-S10] Diagnose host constraints without claiming precise background timing everywhere.
Safe mode disables optional widgets/integrations for the editor, preserves original documents, and offers diagnostics/export; it is not permission to silently alter published output. Interrupted database upgrades record before/after version, last completed batch, original snapshots and failure reason. A copied staging site must not reuse production credentials to overwrite the original's mappings. A deactivated plugin retains data, but its removed PHP renderer cannot be promised to keep dynamic output identical.
17. Connected publishing and editing authority protocol
17.1 Setup and installation binding
Connect through a flow proving control of the WordPress installation and authorized cloud site. Negotiate protocol versions, document/widget ranges, endpoint URLs, media limits, supported activation guarantees, permission scope, and installation/blog identity. Distinguish configured, verified, degraded, revoked, and incompatible. Show measured check time and safe failure category.
Store outbound secrets encrypted via a separate key/secret service, not as unrecoverable hashes when later requests need the secret. Store verification-only token hashes where appropriate. Use separate signing keys for webhook delivery. Support rotation with key IDs and a short, controlled overlap; test interrupted rotation and revoked credentials in queued jobs.
A copied WordPress database can copy installation credentials and identity. Treat changed canonical URL/blog binding, conflicting instance activity, and explicit clone detection as reasons to require re-binding. A perfect clone cannot always be detected from copied software state alone; make the protection assumptions explicit and provide admin-confirmed clone reset. Do not overwrite original mappings automatically.
17.2 Single editing authority
Store authority owner, epoch, last agreed source revision, last observed destination revision, and pending handoff state. Both hosts enforce the epoch on managed writes. Source save and destination activation also need current resource revisions. A status banner is not enforcement.
Use a handoff state machine: ACTIVE_AT_SOURCE → FREEZING → COPYING → DESTINATION_READY → COMMITTING_NEW_AUTHORITY → ACTIVE_AT_DESTINATION. Persist each acknowledgement. Recover interrupted transfers by querying both states, not by granting both writers. During partitions, prefer a visible write restriction or fork over silent conflicting ownership.
For emergency takeover, an administrator explicitly fences the old connection, establishes a new authority generation that cannot be mistaken for a restored old one, and records preserved source/destination snapshots. The old side remains unauthorized when it reconnects. There is no generic conflict-free automatic merge in this scope.
17.3 Transfer and activation envelope
The proposal carries operation ID, installation/blog identity, connection generation, page mapping, source revision/hash, release ID, schema/renderer/widget versions, expected destination revision, authority epoch, environment, and asset manifest. Required assets are uploaded/reused by verified checksum and ownership; actual destination IDs are returned and persisted. Internal links and slugs are remapped with a report.
The destination stages without overwriting active output. Activation validates authentication, capability, current epoch/revision, idempotency identity, and prepared payload. It records the effect receipt in the same local commit boundary as the managed pointer change. Repeating the same operation returns its receipt; changing its payload is rejected.
After a timeout, the source queries the operation endpoint. A missing receipt is not immediately proof of no effect if the destination contract permits uncertainty; query the active state and reconcile according to the protocol. Unsupported old plugin versions receive an update-required or read-only response, not a destructive best-effort overwrite.
17.4 Destination verification and security
Perform a bounded authenticated read-back and public-route verification using the returned remote URL only after validating it. Enforce HTTPS, allowed ports/schemes, validated DNS/IP connection targets, redirect checks, and network egress policy. A regex or hostname prefix is not complete SSRF protection. Apply the same policy to media import, preview fetching, and webhooks. [S33]
Never forward credentials across unapproved redirects. Protect against requests to loopback, private, link-local, metadata, and internal platform services including IPv6 and alternate encodings. Recheck on redirects and actual connection establishment. Preserve TLS hostname verification when pinning a validated IP. Customer-private networking is a separately authorized connector feature, not a bypass switch on the public service.
17.5 Authority shared-resource and release rules
Per-page ownership is insufficient when pages use a shared header, token library or route map. Version 4 treats each shared resource as independently owned and revisioned; a release pins its allowed version. The initial connected product does not promise editing a WordPress-owned global component from a cloud-owned page. Offer a locally owned copy or explicit resource-authority transfer with a compatibility report.
An authority epoch is a destination-enforced trust generation, not just a number painted in the UI. A handoff has one transfer ID, source freeze revision, both host receipts and an explicit commit decision. If either side is unreachable, keep managed writes restricted for that resource or create a new unconnected fork. After emergency recovery, require fencing or re-binding; a restored old cloud counter must not be treated as newer than the destination's trusted state.
Before executing a queued connection task, resolve the current canonical destination and secret reference from the connection record. Do not trust a user-supplied URL stored in a job. URL changes, clone warnings, permission changes and credential rotation can invalidate a previously prepared request. Pin the allowed destination scope, but never keep using a revoked secret merely because it was valid when queued.
17.6 Connected first publication and update examples
First publication: establish real installation capabilities; verify page-create scope; upload assets using operation-scoped deduplication; request a prepared remote page; store the actual returned post ID; stage document and native metadata; activate the managed snapshot; complete required native status/route effects; obtain receipt; verify actual URL and active hash. If creation succeeded but mapping persistence failed, locate the remote page by operation identity before creating another.
Update: load existing mapping, source revision and observed destination generation; stage against the mapped page; activate only if generation/authority remain unchanged; report conflict when a local administrator changed destination content. An explicit override must be a new authorized operation with the current destination precondition, not a hidden retry that refreshes the precondition behind the user's back.
Asset reuse is local to the authorized destination and verified checksum; remote IDs are strings at the protocol boundary. Media-offload, multilingual routing and SEO integration are advertised only for tested combinations. Verification of a destination URL must retain SSRF defenses, even when that URL was returned by the remote host.
18. Durable jobs, operation tables, and recovery algorithm
18.1 Authoritative state
Persist business operations and steps in PostgreSQL. Queue records are delivery hints that can be reconstructed. Logical storage includes operations, steps, attempts, outbox events, per-sink deliveries, inbound events, effect receipts, scheduled occurrences, and resource reservations. A separate failed-operations view may be sufficient; avoid duplicating status into inconsistent tables.
An operation owns tenant scope, actor/service policy, immutable inputs, request hash, idempotency key, destination, deadlines, workflow version, and overall state. Steps own status/version, lease owner/token/expiry, dispatch generation, attempt count, result references, and error classification. Receipts own the external effect identity and observed outcome.
A queue envelope contains only job type/version, operation ID, step name, dispatch generation, and tracing context. Load authoritative scope from the operation and validate references. Do not put full documents, passwords, or unnecessary personal data in queue payloads. BullMQ stores job data in Redis; protection is an application responsibility. [S06]
18.2 Dispatch and execution
The dispatcher claims due delivery rows in a short transaction with atomic claiming semantics, commits the claim, and enqueues outside that transaction. It records acknowledgement or retry state afterward. A crash after enqueue can cause duplicate delivery and must be expected.
A worker validates payload version and claims the durable step with an expected state/version. It loads pinned inputs, checks permission and current destination scope, performs bounded work, and persists the result/receipt plus next-step outbox in a transaction. It acknowledges transport completion only after durable business persistence. Do not hold SQL locks while compiling or waiting for remote HTTP.
A recovery process scans nonterminal operations, expired leases, undispatched steps, and uncertain effects. It must operate even when the Redis queue is lost; the control process should be able to inspect PostgreSQL directly, not depend solely on scheduling itself through the failed broker. Before re-dispatching a side effect, inspect receipts and destination state.
Lease timeout gives another worker the right to investigate or continue, not proof that the old worker stopped. Activate only with destination-enforced guards. Define which worker failures can rebuild pure output and which require reconciliation. Retain workflow-version handlers or migrate in-flight workflows explicitly during platform upgrades.
18.3 Retry ownership and state
Use one authoritative business retry schedule. The PostgreSQL step's next-attempt time and budget are the controlling values; configure transport retries narrowly so a second retry layer does not multiply attempts unexpectedly. On a worker crash, transport redelivery consults the durable step and does not bypass its backoff or authorization.
Candidate transient schedule: 2, 10, 30, 120 and 300 seconds with jitter, bounded by step/operation age. Honor a valid bounded Retry-After for destination throttling. Authentication, schema, capability and conflict failures do not enter endless network retry. Set separate connect, request, step, operation, and shutdown deadlines. Permanent failures remain retained and actionable.
A manual retry requires authorization and checks whether the original input/approval remains valid. Reuse the logical operation for a genuine continuation; a changed document is a new operation. Cancellation after an uncertain effect becomes reconciliation, not deletion of evidence. Dead-letter/quarantine entries retain safe reason, input references, attempts, owner, and permitted recovery action.
18.4 Scheduling and fairness
Schedules use IANA timezone, stable occurrence identity, next due time, schedule version, and explicit misfire/DST behavior. Multiple schedulers create one operation per unique occurrence. Store timestamps in UTC for ordering while retaining the user's timezone intent. A schedule change invalidates obsolete future occurrences without altering completed history.
Separate interactive publication, bulk import/media, external delivery, and recovery capacity. Enforce per-account and per-destination concurrency, cost-weighted admission, global ceilings, and reserved recovery slots. Do not assume a library edition automatically provides fair scheduling. Implement and test the policy or explicitly select a supported feature. [S35]
18.5 Due-work claiming reference pattern
Use an indexed due-work query with a bounded batch and row locks. PostgreSQL documents SKIP LOCKED as useful for queue-like consumers while warning that it does not provide a consistent general-purpose view. [V4-S11] A representative dispatch claim is:
WITH due AS (
  SELECT id
  FROM outbox_deliveries
  WHERE delivered_at IS NULL
    AND eligible_at <= CURRENT_TIMESTAMP
    AND (claim_until IS NULL OR claim_until < CURRENT_TIMESTAMP)
  ORDER BY eligible_at, id
  FOR UPDATE SKIP LOCKED
  LIMIT $1
)
UPDATE outbox_deliveries AS d
SET claim_token = $2,
    claim_until = CURRENT_TIMESTAMP + INTERVAL '30 seconds'
FROM due
WHERE d.id = due.id
RETURNING d.id, d.event_id, d.sink, d.claim_token;

This reference statement assumes an authorized dispatcher role, matching schema/indexes and an enclosing short transaction. Commit before contacting Redis. Record delivery only when the same claim token still owns the row; never let a late claimant mark a later claim complete. A reclaim can legitimately produce duplicate transport jobs. Transport job IDs should be derived from stable operation/step/dispatch generation without depending on library-specific forbidden characters; validate against the pinned queue library.
Worker claims are a separate conditional update of operation-step state. Initial candidate lease is 30 seconds with heartbeat every 5 seconds; use database time for ownership decisions, not unsynchronized host clocks. Long pure builds checkpoint or heartbeat through a separate nonblocked control loop. Loss of a heartbeat causes recovery investigation; it is not proof the old process ceased all external effects.

20. Redis, caching, admission, and transport policy
20.1 Two Redis roles
Use separately operated or independently resource-isolated redis-jobs and redis-cache, not just numbered databases on one server. Queue Redis uses persistence, noeviction, memory headroom, protected networking/TLS where supported, and tested failover. Cache Redis uses bounded expiring rebuildable values with an explicit eviction policy. BullMQ's selected Redis backend requires queue keys not to be arbitrarily evicted. [S06]
An every-second AOF policy can lose recent writes in the documented failure model; it is not unconditional zero-loss storage. That is why unfinished operations remain discoverable in PostgreSQL even after successful queue dispatch. Confirm managed-service persistence rather than assuming configuration examples are applied by the provider. [S07]
Do not store the only copy of drafts, sessions/revocations, billing reservations, audit, or receipts in cache. Security-sensitive controls have conservative fallback behavior. A cache outage must not become unlimited login attempts or unlimited AI spending. Rebuildable caches can use source fallback only under concurrency limits to prevent a stampede.
20.2 Cache contract
Keys include tenant/site/revision or immutable public release identity. Permission-sensitive cache entries are scoped to the relevant policy generation and cannot authorize critical writes without current policy. Use request coalescing, jittered expiries, negative-cache rules, and measured stale-read policies. Public and private caches are separate trust boundaries.
Ephemeral presence/progress notifications are not operation history. Reconnect reloads status from the durable API or a persisted event cursor. Do not equate a missed websocket/Pub/Sub message with a lost job. Keep operation authorization on reconnect and every status read.
20.3 Admission and resource protection
Before accepting expensive work, check per-account pending count/cost, per-destination limits, global storage/outbox headroom, and reserved recovery capacity. Reject safely with a typed retryable or quota error before durable acceptance when limits are exceeded. Once accepted, retain the operation and communicate delayed execution rather than silently discarding it.
Candidate high-water policies should cover queue memory, database outbox bytes/age, object staging growth, maximum simultaneous builds, and provider throttling. Do not scale workers into a destination outage. Detect prolonged dependency failure and open a scoped circuit breaker while preserving pending work. A health check immediately before a write cannot guarantee the write will succeed; each operation handles its own failure.
20.4 Fair admission and workload priority
Use four priority classes: integrity/recovery; interactive save and authorized activation; normal admitted publish; bulk media/import/optional AI. Priority does not bypass tenant permissions or promise that a running external effect can be interrupted. Reserve at least one control/recovery execution slot per deployment group in the initial profile, independently of build saturation.
Implement a dispatcher policy that rotates over eligible accounts with cost-weighted credits, a maximum active-task count, and a per-destination cap. Initial candidate caps are two running pure builds per account, one activation per site/environment/destination, four media tasks per account, and one WordPress write stream per connection. These are safe starting policies to validate, not universal provider limits. A large account may have a reviewed higher tier, but ordinary users must not be starved by an unlimited bulk queue.
Credits refill at a bounded rate; account weights are configuration with audit, not trusted client fields. Estimate task cost from document nodes/pages/media bytes and correct it with measured consumption. Bound estimation error through hard wall-time/memory and operation deadlines. Recheck circuit state at dispatch and effect time. A down destination moves only its affected work to dependency-wait; it must not stop other WordPress sites.
New-work admission reads durable account reservations and global high-water summaries with a conservative fallback. Define 'reject before acceptance' separately from 'accepted but delayed'. Candidate warning levels start at 70% storage/queue-budget use and restrictive admission at 85%, but actual thresholds must account for provider limits, forecast growth and retained accepted work. Disk or WAL exhaustion can happen even with a low job count.

21.3 Public forms and dynamic runtime
Forms submit against a published form schema/revision, not arbitrary field instructions from the client. Use a narrow public runtime API, per-form/site limits, field/file size limits, spam controls, optional challenge, and validated destination routing. Anonymous forms do not authenticate as the site owner. Protect user-specific forms with appropriate access control/CSRF. Store accepted submissions durably before showing accepted; notification delivery can follow asynchronously. Display accepted versus sent/delivered separately. Keep personal information out of general logs and queue payloads; define export, access and deletion rules. Cloud and WordPress forms can use their native storage/runtime, with opt-in connection rather than mandatory CRM coupling.
21.4 Core wire contracts selected for Version 4
Use an explicit command-style draft save to remove ambiguity around server normalization and HTTP representation validators. GET .../draft returns the current document plus opaque revision. Existing PUT routes may temporarily delegate to the same application operation through a versioned compatibility adapter; they are not a second persistence implementation.
Use 412 only when an endpoint actually implements a failed HTTP If-Match precondition, not merely because a body field is stale. HTTP conditional semantics and Problem Details are documented in RFC 9110 and RFC 9457. [V4-S13][V4-S14] Do not return a misleading ETag for a transformed representation. The adapter consumes the explicit returned revision and mutation receipt.

21.6 Error catalogue, idempotency and reconnect
Problem responses use type, title, status, detail, instance, plus safe code, requestId, retryable and bounded field/conflict details. Use 400 for malformed envelopes, 401 unauthenticated, 403 forbidden, 404 for unavailable scoped resources, 409 for domain/revision/authority/idempotency conflicts, 413 for excessive bodies, 415 unsupported media, 422 for valid JSON failing semantic validation, 429 for enforced client/account admission limits, and 503 for temporarily unsafe platform capacity or required dependency failure. Adopt one consistent disclosure policy for unauthorized resource existence.
After authentication, idempotency lookup is scoped to tenant, actor or permitted service policy, method/action and resource. It binds the request hash and immutable payload. It cannot leak another user's response, skip current read authorization, or alter the current head during replay. Candidate client retry horizon is 24 hours with at least seven days of protected request receipts; align external receipt retention with longer recovery requirements. After documented expiry, automatic replay is not assumed safe.
For progress, initially use status polling with a server hint, backoff and conditional response where supported. Add SSE only when useful: per-operation monotonic event sequence, Last-Event-ID reconnect, a bounded retained event window and authenticated subscription. A too-old cursor returns a fresh snapshot/reset marker. Do not put session secrets into logged stream URLs. A progress percentage is completed known work divided by total known work; otherwise show stage and completed items, not a fabricated percentage.
Concrete body bounds
The core page document cap is 2 MiB UTF-8 serialized bytes. The containing draft-save request has a separate 3 MiB cap so envelope overhead does not contradict the document limit. Controlled webhook bodies initially cap at 1 MiB, ordinary form data at 64 KiB, and returned validation issues at 100. Configure reverse proxy, API and plugin consistently, using the smallest actual host limit; respond with a typed limit error instead of accepting an unbounded body. Binary media uses the separate upload protocol, not embedded base64 in page JSON. The reference samples use illustrative all-zero digest values; they are not observed release receipts.
22. SaaS billing, entitlements and account lifecycle
22.1 Commercial scope and ownership
Model billing at the account boundary and collaboration at the workspace boundary. Personal users receive a personal account/workspace. Agency accounts may own several workspaces, but a workspace membership must not automatically confer access to the agency's invoices, payment methods or other clients.
Separate Subscription, Entitlement, UsageReservation, UsageEntry, InvoiceReference and provider-event receipt. Store provider identifiers, not raw payment-card details. Select a payment provider after evaluating required markets and commercial terms; this blueprint does not claim a compliance certification or choose a provider on the user's behalf.
Entitlements answer what a customer may use; permissions answer what a specific actor may do. A paid plan does not bypass a denied permission. An editor's local UI feature flag is not the source of commercial authorization.
22.2 Durable usage and reservations
Reserve constrained resources before accepting expensive work. A reservation includes account, operation, unit type, maximum quantity, policy version and expiry/reconciliation state. Use an atomic database decision so simultaneous uploads cannot each spend the same remaining quota. Finalize against measured usage, release unused capacity, and reconcile abandoned operations; do not expire a reservation blindly while its external effect may still be running.
Record adjustments as auditable compensating entries rather than silently editing historical usage. A retry of the same business operation must not create another charge. Distinguish billable product units from operational processing attempts, and disclose the charging policy. Best-effort visitor analytics is not an authoritative billing ledger.
For AI, reserve a bounded request budget, cap requested output/work, record provider receipts when available and reconcile uncertain consumption. An HTTP timeout does not establish that the provider consumed no resources. Do not promise a mathematically exact spending cap when a provider cannot enforce or report the required boundary; adopt a conservative reserve and documented exposure limit.
22.3 Payment events and customer lifecycle
Verify provider signatures according to the provider's documented raw-body protocol, persist events before acknowledgement, and apply idempotent state transitions. Provider events can arrive repeatedly or out of order; Stripe explicitly documents both conditions. Reconcile against authoritative provider state when necessary instead of assuming arrival order is billing order. [S25]
Define trial, active, past_due, grace, restricted, cancelled and deletion_pending behavior. Keep cloud billing failure separate from a customer's independently installed WordPress core. For cloud downgrades, block new over-quota work according to the published policy, preserve content, provide export and explain any serving restriction before its contractual effective time. Security or abuse suspension is a separate process and may need a different response.
Commercial release gate: duplicate payment events, out-of-order transitions, simultaneous quota reservations, refund/adjustment flows, cancellation and provider downtime all pass. Until then, operate only an explicitly non-billing pilot rather than presenting an unverified subscription workflow as production ready.
22.4 Reservation and settlement transaction detail
Account-budget row contains unit type, period, allocated, reserved, consumed and policy version. A reservation transaction conditionally increments reserved only when allocated minus reserved minus consumed covers the requested maximum; insert a unique (account,operation,unit) reservation in the same transaction. Simultaneous attempts serialize on the relevant budget row, not a global customer lock. Record retryable contention separately from a true insufficient-budget decision.
After a confirmed effect, settlement atomically moves reserved to consumed according to the declared product unit and records a unique ledger entry. Release remaining reservation in that transaction. A retry cannot settle twice. External consumption above estimate is handled by an explicitly bounded exposure policy, not silently allowing a negative budget. Reconciliation resolves expired or cancelled reservations only after checking whether associated effects may still be running.
Commercial plan changes create an entitlement version and effective time. They do not change historical reservations silently. A queued publish may proceed or block according to its recorded policy and current safety/access rules; communicate the adopted rule. Provider callbacks are facts to reconcile, not instructions to grant whatever plan a client supplied. Stripe documents duplicate and unordered webhook delivery, so arrival order is not a sufficient subscription state machine. [V4-S15]
23. Privacy, retention, deletion and data ownership
23.1 Data inventory and policy
Maintain a register of identity data, private documents, published content, form submissions, connection credentials, audit records, operational logs, exports, backups and optional AI context. Each entry identifies controller/operator responsibility, purpose, region, access roles, retention, deletion method and subprocessors. Applicable legal requirements require qualified review for the actual launch markets; this plan is not a legal opinion or automatic GDPR/DPDP compliance assertion.
Proposed operating defaults, subject to approval: time-limited private export URLs, bounded diagnostic retention, explicit form-submission retention, documented backup expiry and a narrow audit retention policy. Do not invent one retention period for every data class. Avoid credentials or unnecessary personal data in logs, traces, Kafka topics, dead-letter payloads and support bundles.
23.2 Export and deletion as tracked operations
Exports pin an authorized snapshot, include portable documents/assets and a compatibility manifest, exclude secrets, and produce a private expiring result. Recheck permission before issuing the retrieval link. Separate portability exports from forensic/admin exports.
Deletion progresses through verified request, access restriction where appropriate, retention/hold evaluation, live-store deletion, object/projection/cache cleanup, subprocessor actions and receipt collection. Stop scheduled jobs and revoke applicable credentials so deleted content is not recreated by a delayed worker. Record a deletion tombstone or equivalent minimal suppression record without retaining the deleted content itself.
A deletion request is not complete merely because one database row disappeared. Account for replicas, object versions, retained releases, exports, search projections, queue references and backups. Backup expiry and lawful holds may delay physical removal; state those limitations accurately. “Crypto-erasure” is not an automatic substitute unless the actual key hierarchy and every readable copy support that guarantee.
23.3 Prevent resurrection after restore
Preserve the minimal deletion/revocation suppression ledger through a separately protected recovery mechanism. On restore, replay post-snapshot deletion and credential-revocation actions before re-enabling public access, exports or workers. Verify the ledger's freshness against the incident's recovery point. Missing suppression history creates a release block, not permission to expose stale personal data.
Native WordPress includes appropriate exporter/eraser integration for plugin-owned personal data, local retention controls, uninstall choices and diagnostics that redact secrets. A disconnected local WordPress owner remains responsible for their host's backups; cloud deletion cannot truthfully erase independent local copies without an authorized connected operation and receipt.
23.4 Suppression ledger and export controls
A suppression entry uses a minimal stable resource/account identifier, request ID, monotonic lifecycle version, effective time and action class. It contains no deleted document body or unnecessary contact data. Replicate/protect it through a recovery mechanism whose freshness is verified before restoring customer access. A stale backup cannot simply replace this newer ledger.
Export preparation pins the authorized revision set, uses private storage, records its ownership and expiry, and rechecks access before issuing a retrieval grant. Deletion/revocation can block future download grants but cannot recall bytes already downloaded or necessarily revoke a still-valid presigned URL instantly. Set a short link lifetime and document that limitation. A connected cloud deletion records which remote copies were actually deleted and which independent WordPress installations remain outside its authorized control.
Data-retention values are per class: drafts/revisions, published artifacts, operations/receipts, form submissions, billing records, diagnostics and backups. The implementation must not replace qualified market/legal review with a universal invented retention period. The proposed operational timers in this document are engineering defaults, not legal retention advice.
24. Security engineering and supply-chain control
24.1 Threat model and verification register
Use OWASP ASVS as a verification catalogue and map applicable requirements to implementation and executed tests. Target an ASVS Level 2-oriented baseline with additional controls for administrative actions, credentials, tenant isolation and release activation. This is a proposed verification scope, not an ASVS certification or a claim that every requirement already passes. [S04]
Threat-model at least these actors and boundaries: anonymous visitor, authenticated tenant, malicious tenant editor, compromised integration, compromised worker, support administrator, CI runner, WordPress administrator and infrastructure operator. Model credential theft, cross-tenant reads/writes, malicious imports, SSRF, unsafe SVG/HTML, account takeover, resource exhaustion, forged receipts, cache poisoning, restored stale credentials and dependency compromise.
Create explicit negative tests for object access by guessed IDs, mass assignment, unauthorized operation retries, stolen expired export links, cache key collisions, tenant context leakage through connection pools, redirect-to-private-network fetches, and customer scripts targeting the editor's cookies or message bridge.
24.2 Runtime privileges and key management
Use short-lived workload identity where supported. Separate API, dispatcher, build, media, external-connection, activation, cleanup and migration privileges. A renderer requires read access to pinned inputs and permission to write staged output, not permission to publish every site or read every connector secret. Separate service accounts alone do not establish per-tenant isolation; constrain retrieval and object permissions through tenant-scoped repositories or narrowly issued capabilities.
Protect recoverable secrets with a managed secret service or envelope encryption, key versioning, rotation, access audit and tested recovery. Avoid storing decryption keys with the same unrestricted database backup. Application-visible Kubernetes Secrets need encryption-at-rest and access controls; base64 representation is not encryption. [S32]
A compromised signing key requires revocation and re-establishment of trust; blindly retaining old keys forever defeats rotation. Test key overlap windows, expired keys, replay windows, installation identity and recovery when the key service is unavailable.
24.3 Vulnerability and supply-chain process
Require dependency/secret/static analysis, targeted dynamic security testing, container scans, plugin coding/static analysis, license inventory, SBOMs and authenticated artifact provenance. SLSA provides a useful model for build provenance and build-system assurance; generating a document called an SBOM alone does not establish trusted provenance. Verify the producer, source revision and digest at deployment. [S31]
Review third-party dependencies for maintenance, support, licensing and required runtime privileges. Automate update proposals, not unreviewed production upgrades. Set an incident-based patch policy: triage actively exploitable critical issues immediately, restrict exposed features where needed, and record owners and deadlines. Any numeric response target must match the support team's actual staffing.
Allow security researchers to report vulnerabilities through a documented private channel. Keep a disclosure/remediation process and a security contact. An external penetration test supplements, rather than replaces, continuous tenant and authorization tests. Do not waive an unresolved cross-tenant write or credential-exposure defect to meet a launch date.
25. Docker, infrastructure as code and platform release delivery
25.1 Reproducible packaging
Retain Docker/OCI packaging for the API, application workers, heavier build/media workers, controlled migrations and compatibility tests. Use multi-stage builds, locked dependencies, maintained digest-pinned bases, minimal runtime contents and explicit rebuild/update policy. These practices align with Docker's build guidance. [S08]
Run non-root with bounded memory, CPU, process count and writable temporary storage. Use a read-only root filesystem where practical. Do not mount the host Docker socket. Scan and attest the final image actually deployed, not merely the source or an earlier build stage. Pin images by digest in release records.
The browser editor can be served as static assets. The WordPress distribution remains an installable ZIP containing its compiled browser assets and PHP dependencies. Users do not need local build tooling. Compose is a development/disposable-test profile, not an implicit multi-zone production topology.
25.2 Infrastructure ownership
Use one reviewed infrastructure-as-code owner for network, compute, data services, secrets, storage and backup policy. Terraform or an equivalent already-operated tool is acceptable; choose one rather than maintaining parallel conflicting definitions. Validate plans in CI and gate destructive changes. Protect state storage and lock concurrent changes. Separate production and nonproduction credentials and accounts/projects as appropriate.
Provide reference environments for development, integration tests, staging and production. Branch previews use synthetic data and limited secrets, expire automatically and cannot send real customer messages or alter production WordPress destinations. Test data generation must not copy sensitive production data by default.
25.3 Two different release pipelines
Platform release: reviewed commit -> locked build -> tests/scans -> signed/checksummed artifacts -> controlled migrations -> staged/canary rollout -> synthetic journeys -> observation -> expand or rollback.
Customer release: authorized saved document -> immutable content build -> staged artifacts -> verification -> guarded site activation -> receipt and live verification.
Customer content must not modify CI scripts, install arbitrary server packages or alter Kubernetes manifests. Treat content verification and platform code delivery as different trust domains.
Use expand/backfill/verify/switch/contract database migrations and a single controlled migrator identity. Application rollback cannot undo an incompatible destructive migration. Keep old application versions compatible during the declared rollout window, and delay contraction until compatibility is demonstrated.
Canary comparison should measure relevant error rates and user journeys against a control, not merely whether a pod started. Google's SRE workbook describes canarying as a way to reduce release exposure; automated decisions still need meaningful signals and safe rollback boundaries. [S34]
25.4 Reproducible developer and CI commands
Expose one documented workspace entrypoint for install, lint, typecheck, unit tests, contract checks, cloud integration tests, WordPress integration tests, browser tests, performance smoke, build, package plugin and migration verification. The chosen package manager and toolchain are pinned after a clean baseline run. Proposed names are test:contracts, test:integration, test:wordpress, test:journeys, test:performance, build:plugin and db:migrate:deploy; their existence is not claimed in the current repository.
Pull requests run cheap deterministic checks first, then affected integration/browser tests. Main and release candidates run the full critical matrix. A dependency change runs the relevant complete host matrix, not only cached unit tests. Cache CI artifacts by lockfile, toolchain, source and configuration; never reuse test results after their relevant inputs changed. Keep a full-run escape route when affected-test detection is uncertain.
Release artifacts contain the source commit, lockfile digest, schema/renderer/widget/workflow versions, enabled feature manifest and build provenance. The artifact that passed tests is the artifact deployed; do not rebuild an unverified different image during promotion. Docker documents multi-stage builds and related packaging practices; those practices do not certify application behavior. [V4-S16]
25.5 Reference environment manifest
Define development, disposable integration, staging and production as explicit configurations. Development Compose binds database/broker ports to loopback by default and includes separate cache/job Redis services, PostgreSQL, API, selected worker pools, test object store and optional isolated WordPress/MySQL. Resetting test volumes is a separate confirmed command, not a hidden part of startup.
Staging uses representative security, storage semantics and process separation with synthetic tenant data; production data is not copied by default. Production starts in one writing region with tested recovery and managed stateful services. The exact provider, region, machine size and service tier are environment decisions; record them in environment-manifest.json before deriving an SLA or cost claim. The main architecture is not tied to an unverified cheap/free tier.
Critical configuration includes application/environment identity, allowed origins, trusted proxy hops, database/pool settings, queue/cache endpoints, object namespaces, serving-manifest backend, key references, upload/document limits, admitted worker caps, webhook policies and telemetry destination. Validate shape and cross-field consistency at startup, redact secrets, and refuse unsafe production defaults. Never mutate schema during readiness.
26. Kubernetes operating profile and adoption gate
26.1 Adoption decision
Prepare a tested Kubernetes deployment profile, but do not require a newly built Kubernetes platform for the first reliable release. Activate it on an existing well-operated cluster or when independent worker scaling, placement and rollout requirements justify the operational cost. The gate requires a named operator, upgrade policy, incident coverage, cost review and passing node-drain/rollout/failure tests.
Keep PostgreSQL, Redis and optional Kafka in managed data services outside the application cluster initially. This is a risk-reduction choice, not a claim that stateful systems can never run safely on Kubernetes. No customer's local WordPress plugin depends on the cloud cluster.
26.2 Workload configuration
Define deployments for API, control/recovery, release builds, external connections, media/imports and optional projections. Provide resource requests/limits, temporary-storage bounds, topology placement, permitted network paths, workload identities and observability. Enforce the Restricted Pod Security profile where compatible, with narrowly reviewed exceptions; container admission controls supplement application sandboxing. [S11]
A reference production profile can start with three API replicas across actual available zones and reserved recovery capacity. This is not a capacity result. Validate remaining capacity after losing a zone, including database connections and managed-dependency behavior. PodDisruptionBudgets limit eligible voluntary disruptions; they cannot prevent all node or zone failures. [S15]
Separate startup, readiness and liveness checks. An optional Kafka/cache outage should not restart every API instance. Liveness should detect a stuck process; readiness should reflect whether that workload can safely handle its required requests. Workers drain new claims, checkpoint or stop within a bounded grace period, and rely on durable recovery after forced termination. [S16]
26.3 Autoscaling and dependency budgets
Use API scaling based on tested request/CPU metrics. For workers, use KEDA or an equivalent scaler with a metric for eligible, due work and its age. A future scheduled job is not immediate demand; dependency-blocked tasks are not an invitation to scale without limit. KEDA's Prometheus scaler provides a mechanism to use an explicit metric query, but the product must define a correct metric. [S14]
Do not attach two competing autoscalers to the same deployment. Set conservative behavior when telemetry is absent. Essential dispatch and recovery cannot all scale to zero. Enforce downstream connection and rate limits independently of replica count:
sum(maximum replicas × connections per replica)
    + migration/recovery/operator reserve
    <= usable database connection budget

Autoscale only inside measured downstream budgets. Reserve recovery capacity and account-level fairness. Test startup delay, burst response, database saturation, destination outage and metrics failure; these tests determine settings, not a generic internet replica formula.
26.4 Deployment ownership and reference resource budget
Use one infrastructure owner and one application reconciler. The proposed Kubernetes profile uses reviewed infrastructure modules and Helm workload configuration; Argo CD is optional only when the platform team chooses it as the single application deployment owner. Do not have CI and a reconciler repeatedly overwrite each other's settings.
Reference sizing begins as a measurement plan, not purchased capacity: API process 1 vCPU/1 GiB; pure build process 2 vCPU/2 GiB with one measured CPU-heavy task at a time; media process 2 vCPU/2 GiB with one isolated parser at a time; connection worker 1 vCPU/1 GiB with limited I/O concurrency; control/recovery 0.5 vCPU/512 MiB. Actual Kubernetes requests/limits require profiling and can differ; enforce CPU, memory, process and ephemeral-storage ceilings in the chosen runtime. Avoid packing critical recovery with evictable bulk work.
Example connection budget: three API replicas times ten connections, two control replicas times three, four build replicas times two, four connector replicas times three, and two media replicas times two consume 60 potential database connections; reserve another 20 for migration/recovery/operators and compare 80 against the provider's usable limit. This is illustrative arithmetic, not a claim of sufficient resources. Maximum autoscaling settings must preserve the budget or use a tested pooler configuration.
Kubernetes HPA scales on configured metrics; it does not infer provider limits or database connection safety. [V4-S17] A queue-aware scaler uses due eligible work and age plus a downstream headroom cap. KEDA can supply an external-metric mechanism, but the query must describe real eligible work. [V4-S18] Keep minimum recovery capacity. A PodDisruptionBudget controls eligible voluntary disruptions, not every fault or shortage. [V4-S19]
26.5 One-zone loss and controlled rollout acceptance
At the adopted peak reference workload, remove a node/zone or its equivalent in a controlled test. Confirm remaining API capacity, warm-up time, connection ceilings, worker reclaim, scheduler duplication safety and managed dependency behavior. Existing public static output should not depend on replacement editor pods. Test loss of metrics as a separate scenario: a safe fallback must not scale essential workers to zero or multiply blocked provider requests.
Rollout first a controlled cohort, compare meaningful save/publish metrics to the control, then expand. Roll back application code only within compatible schema/workflow windows; otherwise stop rollout and use a forward repair. Canary health is not merely readiness=200. Store explicit pause/admission controls so a bad release can stop new publication without deleting accepted work or blanking existing sites.
27. Kafka and optional replayable projections
27.1 Keep task commands separate from facts
Retain Redis-backed BullMQ as the selected initial task transport. Kafka is an optional retained event-distribution tier for independently owned analytics, reporting, search projections and activity feeds. RabbitMQ remains an alternative task broker, not an additional mandatory hop. A workflow engine is a separately justified replacement for complex orchestration, not another default component.
Write business events in the same transaction as the state they describe. Dispatch task outbox and event outbox deliveries independently; a task enqueue must not mark a Kafka delivery complete. Kafka unavailability delays projections within finite outbox capacity, not synchronously blocks an ordinary page save.
Suggested topic families remain site-events.v1, release-events.v1, asset-events.v1 and usage-events.v1. An event contains identity, schema version, tenant context, aggregate/version, occurrence time and minimal non-secret data. Never place complete private documents, raw credentials or unnecessary personal data in broad event streams.
27.2 Ordering, replay and data retention
Kafka provides ordering within a partition, not a global ordering of all events. Design routing keys and relay ordering explicitly. Consumers use event deduplication and aggregate-version rules. For full-state replacement projections, reject stale versions. For deltas, detect and recover gaps; do not skip missing deltas as though they were harmless. Kafka's transaction guarantees do not automatically cover arbitrary WordPress or email effects. [S12]
For a PostgreSQL projection, commit the inbox marker and projection change together before committing its Kafka offset. Replaying an already-applied event becomes a no-op. Consumer rebuilds require a retained snapshot plus events covering the gap, or another authoritative backfill; seven days of event retention cannot recover a month-long absence alone.
Privacy deletion must reach projections, archives and replay sources. Keep suppression/version checks so replay does not resurrect deleted content. Authoritative billing usage stays in its ledger; noisy page-view telemetry uses a separately bounded ingestion path rather than adding one synchronous editor-database outbox write per impression.
27.3 Adoption and operations
Enable Kafka when independently owned consumers require retained replay/fan-out or measured throughput/retention economics justify it. Choose a supported managed service/client combination and test effective producer/broker settings. A candidate profile uses three replicas, minimum in-sync replicas of two, acks=all and supported producer idempotence; these are conditional failure-model choices, not an unconditional zero-loss promise. [S13]
Define topic ACLs, schemas, quotas, record bounds, retention, storage alerts, consumer ownership, lag objectives, poison-event quarantine and controlled replay. Outboxes have high-water limits. Never drop required billing, audit or publication facts silently to keep dashboards green. Optional lossy telemetry must be explicitly classified.
27.4 Event design and Kafka activation decision
Start with a database event outbox and one simple reporting projection. Record real event rate, message bytes, independent consumers, replay horizon, recovery time and estimated operating cost before selecting Kafka. Kafka is not needed to make one draft save fast. Retained partitioned events and broker transaction semantics are useful when those requirements exist; they do not make arbitrary remote effects exactly once. [V4-S20]
For each enabled topic, publish the event schema, routing key, ordering scope, retention, privacy class, maximum size, dead-letter policy, replay owner and projection rebuild method. Do not allocate a topic per tenant by default or emit full private documents. Task queue and event outbox have independent delivery receipts. A broken analytics consumer may lag without blocking publication while finite outbox headroom remains safe.
A projection using deltas rejects/repairs gaps; a full-snapshot projection can replace only with a newer aggregate version. Replaying after deletion first checks suppression version. A consumer offset is not the sole business deduplication record. Quarantine poison events with safe payload references and an owner; do not skip billing facts to make lag appear healthy.
28. Backup, disaster recovery, regional fencing and cells
28.1 Recovery scope and target
Adopt the candidate RPO/RTO only after an executed drill. Separate in-region acknowledged-write durability, regional recovery point, public serving continuity and individual WordPress-host recovery. PostgreSQL synchronous replication can reduce a defined acknowledged-write loss window at an availability/latency cost; asynchronous replicas do not establish the same guarantee. Configure and test the chosen commit/failover behavior rather than inferring it from the word “managed.” [S10]
Recover database state, media originals, release objects, manifests, key access, receipts, suppression records, domain bindings and account/authority relationships. Protect independent backup copies from ordinary application deletion. Successful backup scheduling is not evidence of successful restoration.
28.2 Restore sequence
Declare the incident, authorize recovery and stop new dangerous effects.
Fence the old active writers and preserve incident evidence.
Restore operator identity/key access and verify backup integrity.
Restore database and required object versions into an isolated environment.
Apply deletion, revocation and hold changes newer than the snapshot.
Reconcile serving manifests, remote WordPress receipts and in-flight operations.
Verify tenant access, asset references, routes, draft/live separation and authority.
Re-enable serving, then restricted writes, then workers in controlled batches.
Rebuild optional projections and confirm monitoring/customer communication.
Each step has a named role, recorded evidence and an abort condition. Never start every restored worker immediately after importing an old database.
28.3 Fencing must survive loss of the old database
A restored lease counter may be older than values already accepted by destinations. Merely incrementing a counter from an old snapshot does not fence a still-running old region. A recovery activation must establish a newer trusted epoch at the serving/WordPress boundary, revoke old credentials or otherwise prevent the old writer from reaching the effect. Test the actual mechanism.
Do not automatically fail over publishing to a second region when the first region cannot be proven fenced. Preserve read-only published serving where possible and hold unsafe writes. Where a WordPress destination cannot be reached to establish the new authority, keep its writes blocked until reconciliation; avoid a false split-brain availability promise.
For a future regional-cell architecture, assign an account/site to one writing cell. Route read-only delivery globally, keep ownership and region in durable routing metadata, and perform controlled moves with fencing and audit. Start with one production region and a tested recovery region unless requirements justify greater complexity. Multi-cloud and multi-CDN remain separate cost/failure-domain decisions, not automatic launch requirements.
28.4 Drill programme
Before public release, restore a full test account/site into a clean environment and prove publication, assets, revocation, deletion suppression and safe retry behavior. Thereafter propose monthly sample restores, quarterly regional/tabletop exercises and additional drills after material persistence changes, with final cadence owned by operations. Customer promises must reflect achieved results under the declared workload, not the desired target written here.
28.5 Recovery decision tree and anti-replay checks
Separate four incidents: one worker failed; queue records lost; application region unavailable with durable state intact; authoritative database restored to an older point. Only the first two permit routine local reclamation from the current journal. The last case requires suppressions, key/authority and remote effects to be reconciled before writers reopen.
For every recovered nonterminal operation, compare its immutable input, operation identity, destination generation and available receipt. If the destination is ahead, adopt verified evidence or create a conflict; do not reissue the stale operation. If the old writer cannot be proven fenced, keep new publication blocked while safe read-only serving continues. A reset local counter is never itself a trusted new epoch.
A restore drill must contain a deleted account, revoked connection, active release newer than the snapshot, an uncertain remote operation, a pinned media object, and an expired export grant. Validate all six before claiming that restoration is complete. Encryption-key recovery and retention versions are part of the drill; a database backup without readable required keys or objects is not a usable recovery result.
29. Observability, error budgets and operational controls
29.1 Measure the user outcome
Instrument request -> revision -> operation -> step -> destination -> receipt using correlation IDs and trace context. OpenTelemetry supplies instrumentation and signals; choose one operated backend for metrics, logs and traces rather than assuming instrumentation alone provides retention and dashboards. [S36]
Track save success and latency, accepted-to-first-claim time, oldest due outbox item, unfinished-operation age, lease expiry, retries by reason, destination authentication/rate failures, build duration, verified-live completion, reconciliation age, storage headroom and database pool saturation. Separate platform-caused failures from destination-caused failures in diagnosis while also showing the end-to-end customer experience.
Keep tenant and operation IDs in protected logs/traces, not unbounded metric labels. Scrub bodies/secrets and sample expensive traces deliberately. The audit ledger is independent of diagnostic sampling; a sampled trace cannot be the only evidence for an administrative action.
29.2 SLO definitions and release policy
For every adopted SLO, specify event numerator/denominator, time window, measurement location, planned exclusions, affected hosting mode and alert owner. Report low-traffic uncertainty and missing telemetry. A percentage without a measurement definition is not an engineering commitment. Google's SRE guidance explains defining service-level indicators/objectives and using error budgets to govern reliability work. [S01][S03]
Use multi-window error-budget burn alerts for important user journeys and alerts on unrecoverable data/security risks regardless of traffic. A queue-length alert is insufficient when a small number of jobs can remain stuck for hours. Reserve immediate escalation for threatening user outcomes and actionable dependency conditions rather than paging on every CPU fluctuation. [S02]
Proposed policy: pause nonessential release expansion when the service has exhausted its adopted error budget or a canary crosses agreed failure thresholds. Security fixes and incident remediation may proceed with explicit review. Record who can override a pause and why; an override cannot erase evidence or waive an unresolved integrity violation.
29.3 Operational interface
Build a scoped Operations screen showing accepted time, source revision, stage, attempts, destination receipt, last verified state, next retry, cancellation boundary and recovery actions. Account operators see only their scope. Platform staff require audited temporary access. Never expose raw queue administration or credential payloads publicly.
Support safe actions: reconnect destination, retry after reconciliation, cancel before effect, pause new publication, inspect compatibility report and activate a retained release. High-risk bulk retry, tenant data export, key rotation and serving suspension require stronger permission and explicit confirmation. The interface must never label a transport job complete as proof that business publication completed.
29.4 Metrics, alert conditions and user-facing truth
Use bounded labels such as environment, host mode, operation kind, worker pool and result class. Avoid tenant/site/request IDs in every metrics label. Proposed measurements include draft_save_seconds, draft_save_total, publish_accept_seconds, publish_end_to_end_seconds, operation_queue_wait_seconds, outbox_oldest_due_seconds, operation_lease_expired_total, activation_conflict_total, reconciliation_oldest_seconds, build_reused_pages_total, build_compiled_pages_total, worker_memory_bytes, media_rejected_total and db_pool_wait_seconds. Metric names are a proposal, not instrumented code.
Pair the 'fast' metric with correctness: accepted count, eventual verified outcome, rejected admission, timed-out/unfinished operations and duplicate-effect prevention. Do not discard jobs missing the target from the latency denominator. Report platform and destination causes separately for diagnosis while retaining end-to-end user outcome.
Define burn rate as observed bad-event rate divided by allowed bad-event rate. With a 99.9% objective, a 1.44% bad-event rate burns budget at 14.4x. Candidate alerts use both a short and a longer window to avoid paging on one isolated blip; select thresholds through the actual traffic profile. Google's SRE guidance explains multi-window burn-rate alerting. [V4-S21] At low traffic, use dedicated synthetic journeys and report uncertainty rather than pretending zero requests proves availability.
Immediate integrity/security alerts do not wait for an error-budget threshold: false saved acknowledgement, cross-tenant access, unknown old-writer activation, missing pinned content and an invalid suppression ledger trigger containment. Runbook actions must preserve evidence and current live/draft identity.
29.5 Status screen state mapping
Saved: the local sequence equals the latest acknowledged host sequence. Pending publication: durable operation exists but no active destination effect. Building/staging: named progress with item counts. Waiting for destination: dependency-scoped retry with next attempt. Reconciling: an effect may have happened or mandatory evidence is incomplete. Active, checks need attention: destination receipt exists but required verification is unresolved. Published: exact release passed mandatory checks. Superseded/cancelled: no unacknowledged effect remains. Never collapse all these into a green check because an HTTP request returned.
30. Performance, accessibility, SEO and product quality
30.1 Benchmark plan
Benchmark separately: editor responsiveness, API persistence, queue wait, build/transfer time, static delivery, interactive widgets and WordPress runtime. Use named hardware, browser/network profiles, document fixtures, data volume and dependency versions. Publish medians and tail percentiles; averages alone hide stalled saves and expensive pages.
Start with section 7's proposed reference workload, then test bursts, soak, worst-supported documents, mixed tenants, cold caches and degraded dependencies. Load should be open-loop where appropriate so a slow service does not make the generator silently issue less demand. Record generator saturation and offered versus completed work. Set performance regression budgets only after establishing a baseline.
Optimize measured bottlenecks: selective editor subscriptions, lazy inspectors, bounded history, batched reads, useful indexes, object reuse, media variants and isolated heavy tasks. Avoid loading Monaco or the complete editor into published sites. Do not promise all arbitrary customer content will satisfy the same performance budget.
30.2 User-visible quality
Target WCAG 2.2 AA for the editor and shipped default components, with both automated and manual keyboard/screen-reader checks. Customer content can introduce accessibility defects; provide guardrails and publish-time reports instead of promising automatic conformance for every authored page. [S29]
For managed reference pages, adopt Core Web Vitals targets of LCP <= 2.5 seconds, INP <= 200 milliseconds and CLS <= 0.1 at the relevant 75th-percentile field assessment. These are measurement targets, not guarantees before field data exists. Report lab and real-user data separately, and identify third-party scripts/media that affect results. [S30]
Provide semantic headings, descriptive links, image alternative text controls, responsive typography, reduced-motion support, focus visibility and meaningful error messages. Test right-to-left layout and multilingual content if included in the launch scope; use locale-aware routes, date display and content metadata.
30.3 SEO and publishing completeness
Ship real page routes and appropriate status codes, canonical URLs, titles/descriptions, sitemap generation, robots controls, social previews and redirect management. Private previews need authentication and cache isolation; noindex is not access control. Bind SEO metadata and redirects to a release so a rollback restores a coherent route/content set where supported.
For WordPress, avoid conflicting with the theme or an installed SEO plugin. Declare which component owns each metadata output and test supported combinations. Dynamic commerce/search/membership widgets require real runtime integrations, not static look-alike controls that imply working transactions.
30.4 Reproducible benchmark fixtures and scenarios
Fixtures: F-SMALL is a 100-node/25 KiB basic page; F-REFERENCE is 1,000 nodes/about 250 KiB with nested layout, text, tokens, navigation and images; F-LARGE reaches the 5,000-node/2 MiB supported ceiling; F-SITE25 is 25 reference pages with shared header/footer and route map; F-SITE500 tests chunking and manifest scale without promising a 500-page launch tier; F-MEDIA contains valid and boundary-sized files; F-ATTACK contains malformed trees, unsafe URLs, archive traversal and parser-bound inputs. Store generation seed, actual byte sizes, expected graph properties and asset license/provenance where relevant.
Run editor typing/selection/drag/undo for each fixture, a repeated open-close cycle, two-tab conflicts and worker responses arriving out of order. Capture React commit counts, input-to-paint timing, long tasks, worker-message bytes and memory. The stress fixture may have a different supported interaction budget; report it separately rather than hiding it inside an average.
API benchmarks offer an explicit arrival rate using disposable production-shaped data. Test 100 active sessions and 50 saves/second as the base, then a 2x burst, large documents, stale revisions, cold caches and one noisy tenant. Do not allow a slowing load generator to lower offered traffic silently. Record offered, accepted, rejected, completed and failed counts, generator headroom and database pool waits.
Publication tests measure full build, no-change build, one-page incremental change, shared-token change, route deletion, media variant change, cold object cache and failed destination. Include queue wait and activation verification. The no-change build can reuse artifacts but still creates a truthful operation/activation result under the chosen policy; it does not skip authorization or verification.
30.5 Performance gates and measurement discipline
Collect a clean before/after baseline on the same hardware, exact commits, lockfile, fixture seed, browsers, network and dependency tiers. Use repeated runs and store raw samples, not just a screenshot. Initial CI smoke compares obvious regressions; nightly/staging runs measure sustained behavior and statistical noise. A candidate blocking regression is >10% in a stable reference p95 or >20% transfer growth without an approved rationale, provided repeated measurements establish that the change exceeds noise. Do not claim confidence from ten requests at p99.
Measure warm/cold state and failure cases separately. Report sample size and missing data. Profile CPU/allocation/query plans for the bottleneck; optimize one major contributor before changing frameworks. Correctness/security tests run alongside performance. Dropping validation, changing durability, ignoring failed requests or serving the wrong cached tenant can make a benchmark faster and the product worse.
The first optimization order is editor subscriptions and transient-state isolation; route/widget code splitting; safe media variants; bounded API queries and transactions; incremental builds; cache correctness; then worker concurrency and infrastructure scaling. Do not begin with a rewrite to Rust, WebAssembly, a service mesh or globally distributed SQL without evidence that the chosen boundary needs it.
For illustration, if 80% of a path becomes four times faster and the rest is unchanged, total time becomes 0.8/4 + 0.2 = 0.4 of the original, or 2.5x faster overall. This arithmetic explains why a '10x library' does not imply a 10x application. Only measured user journeys establish improvement.
30.6 SEO, content collections and locale completeness
Bind page title, description, canonical URL, social metadata, indexing policy, locale and redirects to the release. Route normalization is versioned: Unicode, percent encoding, trailing slashes, case policy, reserved paths and collision rules are explicit. Preserve old routes through approved redirects; detect loops and long chains. Return real 404/410 behavior instead of serving the app shell with 200 for every path.
For a first-party CMS capability, define collection schema, typed fields, drafts/revisions, published entries, bounded query predicates/sorts, pagination and template bindings. Never accept raw SQL or an arbitrary database/table from widget settings. Static bindings pin a content snapshot and invalidate affected pages when it changes; dynamic bindings name a permitted runtime query and cache/privacy policy. Existing CPT-like UI is not proof of a complete standalone CMS.
For locales, separate translated content from shared style resources, record fallback policy, normalize locale routes and test right-to-left layout/IME behavior. WordPress integration with multilingual or SEO plugins is capability-specific with one metadata owner per field. There is no assumption that every plugin combination works.
Use semantic HTML and first-party widget guardrails. Field Core Web Vitals good thresholds are LCP <= 2.5 seconds, INP <= 200 ms and CLS <= 0.1 at the relevant 75th percentile; they are reference targets, not guarantees for arbitrary customer scripts/media. [V4-S22] Accessibility evaluation targets the declared WCAG 2.2 scope and includes manual keyboard/screen-reader tests; automated checks alone do not establish conformance. [V4-S23]
31. Support, on-call and business operations
Assign role owners for product scope, editor/document, API/data, WordPress, workers, platform operations, security/privacy and QA/recovery. One person may initially hold multiple roles, but each alert and release decision needs a primary and backup. Do not assign real people based on unrelated projects or invent staffing that does not exist.
Define severity and communication rules. A proposed Severity 1 includes confirmed cross-tenant access, lost acknowledged data, widespread serving outage or uncontrolled credential exposure; Severity 2 covers substantial feature failure with a safe workaround; lower severities cover narrower defects. Final acknowledgement/update targets depend on staffed coverage. Never market 24/7 response before funding and testing it.
Maintain runbooks for queue loss, blocked dispatcher, unknown remote activation, database failover, failed migration, expired keys, credential compromise, serving-manifest corruption, domain takeover risk, storage exhaustion, plugin upgrade failure and privacy restoration. Each includes prerequisites, safe read-only checks, actions requiring approval, rollback limits and success evidence.
Provide customer-facing incident status and scoped deployment history. Use a redacted diagnostic bundle containing versions, capability checks and correlation IDs, not complete documents or credentials. Track post-incident corrective actions to closure and repeat the relevant failure test. Blameless analysis is compatible with clear engineering ownership.
Abuse response needs account/site isolation, rate controls and an audited emergency serving-denial mechanism. A legitimate billing dispute must not use the same uncontrolled destructive path as malware takedown. Account closure and site transfer must address scheduled work, credential ownership, domain bindings, shared assets and exports before final deletion.
32. Optional AI, collaboration and extension strategy
AI is optional and operates through the same typed document commands, permission checks and review gates as human edits. Record provider/model configuration, prompt/context references, output provenance and cost receipt as policy permits. Treat retrieved documents, websites and user content as untrusted input. No AI output may directly run server code, install packages, change billing or publish without the relevant explicit authorization.
Keep AI outage and spending limits independent of local editing. Offer a preview/diff, cancelable bounded generation and rollback of accepted document changes. Do not silently train on private customer content or route it to an unapproved provider. Provider retention/data-location choices belong in the privacy register.
Real-time multi-author collaboration is a separate extension. A CRDT can help merge concurrent document operations, but does not determine who owns the cloud/WordPress source, who can publish, or whether a release is approved. Introduce it only with persistence, access revocation, history, reconnect and conflict semantics verified.
Search projections, template marketplaces, developer widgets and third-party Elementor imports are separately scoped capabilities. Trusted first-party widgets ship in the initial runtime. Third-party code needs capability declarations, review/signing, sandbox boundaries, resource budgets, compatibility and revocation. Existing Elementor data/widgets require an explicit translator and coverage report, not a marketing assumption.

33.3 Stop conditions
Block release for cross-tenant exposure, false durable acceptance, unaudited privileged actions, destructive migration, stale-writer overwrite, unrecoverable accepted operations within the declared failure model, broken local-only WP core or an untested required backup restore. Quarantine flaky tests with owners and deadlines, but do not use quarantine to remove a critical gate from scrutiny.
33.4 Contract pack verification versus application verification
The accompanying engineering pack includes proposed schemas, sample requests, an endpoint catalogue, publication state rules, performance budgets, additional failure cases and the dependency-checked implementation backlog. Its local checker validates schema shape, example payloads, sample tree invariants and backlog relationships. These are document/contract checks, not tests of the repository, PostgreSQL transactions, real browsers or WordPress.
Application implementation must port the same fixtures into TypeScript/PHP runtime validation and execute real integration tests. Canonical hash parity requires a tested RFC 8785 implementation on both runtimes; a Python JSON dump or schema check is not evidence of that parity. The SQL patterns in this plan require matching migrations, privileges, transaction boundaries and concurrency tests; they are not a deployable database schema on their own.
Add deterministic interleaving tests for duplicate save/activation, lost response, stale worker, pin/delete, reservation/settlement, permission revocation and old-backup recovery. A small executable state model checks allowed transitions and invariants, but cannot certify unmodelled network/database behavior. Fault injection against real disposable dependencies remains a release gate.
34. Compatibility, versioning and safe updates
Version cloud API, document schema, widget schema, renderer, worker payload/workflow and plugin package independently. Define readable versus writable document versions and actual capability negotiation. Pin exact toolchain versions in release manifests; this document's reference URLs are not instructions to install every referenced version blindly.
Adopt a starting connected-plugin policy of current and previous supported release lines, with an explicit security-maintenance period approved before launch. Publish a machine-readable matrix of WordPress, PHP, database, theme and browser combinations actually tested. Test the minimum and newest supported combinations, multisite and skipped plugin upgrades. Do not label unsupported combinations “compatible” just because activation does not immediately crash.
Old queued jobs must remain readable and executable through rollout or be migrated/rejected into a recoverable state. Version checkpoints and keep the required compatible worker handler until the queue/journal horizon closes. A restarted worker must not interpret an old payload using an incompatible new meaning.
For newer unsupported documents, preserve bytes and offer read-only/export/update guidance. Original documents remain available through the declared migration retention window. Never silently drop unknown widgets to let a save succeed. Update failure preserves local WordPress data and shows a recoverable diagnostic path.
Retain old release artifacts for rollback, but mark a release unsafe when it contains a confirmed exploitable component. A security incident can require a controlled patched rebuild or temporary restriction; immutable history does not mean operators must keep serving a known harmful artifact forever. Document the distinction between exact rollback and patched restoration.
Cloud feature flags require owner, default, audit, expiry and safe fallback. An unavailable flag service cannot disable the plugin's core editing. Remote compatibility checks may restrict unsafe connected writes, not erase locally owned content or impose an undocumented cloud kill switch.

D.2 Runbook: WordPress activation timed out
Entry condition: an authorized operation reached activation, the connection failed, and the outcome is unknown. The current operation/connection must remain scoped to its tenant and destination.
Safe initial actions: pause further activation for the same destination/environment, preserve the operation ID, immutable release hash, expected destination generation, authority epoch and request timing. Inspect existing local receipts. Do not press an unqualified “retry publish” button or create a new operation merely to clear a red status.
Reconciliation: query the destination's authenticated operation receipt. If the operation committed with the expected hash/epoch, persist that receipt and perform bounded live verification. If the destination explicitly shows no committed operation and its revision still meets the precondition, resume the same logical operation through a valid claim. If its content/generation changed, expose a conflict and retain both states. If the destination is unreachable or the receipt cannot establish the effect, keep RECONCILING and route to the documented operator decision.
Cancellation and compensation: a cancelled browser request did not undo an external publish. A rollback is a new authorized activation of a retained release with a fresh precondition, not deletion of history. Check that rollback will not overwrite a more recent independently authorized destination change.
Exit evidence: destination receipt or explicit unresolved/conflict result, final local state, user-facing explanation, audit action and verified draft preservation. Remove the destination hold only when ordering/authority is safe.
D.3 Review discipline
Each implementation review should answer: What is durable? What is the exact effect boundary? What happens after a crash at that boundary? Which identity can retry? Can a stale actor or restored backup repeat the effect? Which test proves the answer? These questions are more valuable than labeling a class “enterprise” or a service “fault tolerant.”
