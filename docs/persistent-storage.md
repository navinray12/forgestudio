# Persistent Media & Asset Storage Guide (Feature 7)

This document describes the persistent storage architecture for ForgeStudio uploads, media assets, backups, and optimized assets.

---

## 1. Storage Architecture Overview

ForgeStudio stores uploaded files (images, backups, optimized media) on physical filesystem storage, while referencing them in PostgreSQL via stable, client-agnostic public URLs (`/uploads/images/<uniqueFilename>`).

* **Database Isolation:** Database records store only public URLs and filenames (e.g. `img_1788268324053_fe78cd15ef1f.png`), never absolute server filesystem paths. This ensures the database schema remains portable and decoupled from host operating systems.
* **Storage Provider:** Controlled centrally via [`backend/src/config/storage.config.ts`](file:///c:/Users/RISSWANTH%20ROY/OneDrive/Desktop/backup/forgestudio/backend/src/config/storage.config.ts).
* **Managed Subdirectories:**
  - `images/`: User image uploads via the Media Library and Website Editor.
  - `backups/`: Durable JSON snapshots generated by the website backup service.
  - `optimized/`: WebP/compressed variants generated by the image optimization pipeline.

---

## 2. Development Setup

In local development, no extra configuration is required.
* **Default Directory:** `backend/uploads/` (or `./uploads` relative to the backend workspace).
* **CWD Agnostic:** Whether the development server is started from the repository root (`npm run dev`) or within `backend/`, the system automatically resolves the storage directory consistently without losing previously uploaded files.

---

## 3. Production Configuration (`UPLOAD_DIR`)

To configure a persistent storage location in production:

1. Define the `UPLOAD_DIR` environment variable in your production environment or `.env`:
   ```bash
   UPLOAD_DIR=/var/data/forgestudio/uploads
   ```
   *(Windows example: `UPLOAD_DIR=D:\ForgeStudioStorage\uploads`)*

2. **Crucial Container Note:**
   > **Setting `UPLOAD_DIR` alone in an environment variable does NOT make container storage persistent.**
   > In containerized platforms (Docker, Kubernetes, AWS ECS, Render, Railway, Fly.io), the container filesystem is ephemeral. You **must** mount an external persistent volume to the path specified in `UPLOAD_DIR`.

### Docker Example:
```yaml
services:
  backend:
    image: forgestudio-backend:latest
    environment:
      - UPLOAD_DIR=/app/data/uploads
    volumes:
      - forgestudio_media_volume:/app/data/uploads

volumes:
  forgestudio_media_volume:
    driver: local
```

### Kubernetes Example:
```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: forgestudio-media-pvc
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 50Gi
---
# In Backend Deployment:
containers:
  - name: backend
    env:
      - name: UPLOAD_DIR
        value: "/mnt/storage/uploads"
    volumeMounts:
      - mountPath: "/mnt/storage/uploads"
        name: media-storage
volumes:
  - name: media-storage
    persistentVolumeClaim:
      claimName: forgestudio-media-pvc
```

## 4. Handling Existing Uploads When Changing Storage Locations

ForgeStudio will **never** automatically delete or overwrite existing uploads. If you change the storage location (e.g. from local development `./uploads` to an external persistent disk):

### Safe Copy Procedure:
1. Ensure the backend is paused or in maintenance mode during file transfer.
2. Copy existing uploads to the new target location preserving subdirectories:
   ```bash
   # Linux / macOS:
   rsync -avz ./backend/uploads/ /var/data/forgestudio/uploads/

   # Windows PowerShell:
   Copy-Item -Path "backend\uploads\*" -Destination "D:\ForgeStudioStorage\uploads" -Recurse
   ```
3. Set `UPLOAD_DIR` to the new path.
4. Restart the backend.
5. All previously created database records and editor image references will continue resolving without needing any database migration.

## 5. Security & Reliability Controls

- **Path Traversal Defense:** All physical file paths are resolved through `resolveSafePath` / `resolveMediaAssetFilePath` with relative boundary checks (`!relative.startsWith("..")`). Arbitrary path navigation or malicious filenames cannot touch files outside `UPLOAD_DIR`.
- **Collision Prevention:** Filenames use cryptographically secure random suffixes (`img_<timestamp>_<hex>.<ext>`), preventing collisions even when different users upload identical original file names.
- **Atomic Cleanup on Failure:** If database asset registration fails during an upload, the written file is automatically removed from disk to prevent storage leaks.
- **Missing File Grace:** If a physical file was deleted externally, deleting the media asset record via the API gracefully cleans up the database record without an unhandled server crash.
- **Asset In-Use Protection:** Deletion checks whether the asset is actively referenced in any website's `editorData` and blocks deletion with `409 ASSET_IN_USE` unless `force: true` is explicitly requested.
